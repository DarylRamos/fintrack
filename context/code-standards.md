# Code Standards

## General

- Keep modules small and single-purpose.
- Fix root causes; do not layer workarounds.
- Do not mix unrelated concerns in one component or route.
- Do not add abstractions until a second real use needs them. External providers are the
  exception, per `architecture.md`.
- All user-facing text is English. Do not add a translation layer.

## TypeScript

- Strict mode is required throughout the project.
- Avoid `any`. Use explicit interfaces or narrowly scoped types.
- Validate unknown external input with Zod at system boundaries before trusting it. This
  includes form data, provider responses, CSV imports and `$queryRaw` results.
- Represent money crossing to the client as decimal strings, and never use `number` for
  it. Calculations go through `lib/money`.
- Amounts come in only through `parseAmountInput` (via `moneySchema`, or `moneyShape` plus
  `.transform(withCanonicalAmount)` in a larger schema, `lib/validation/money.ts`) and go out only through
  `formatMoney` (`lib/money/format.ts`), never `Number(amount)`, `parseFloat` or `toLocaleString`
  (unit 2.1). User input is refused, never rounded. The data layer returns a `Decimal` as the canonical
  string with `toFixed(currencyDecimals(currency))`.
- Currency rules use `currencySchema` from `lib/validation/money.ts`, the one currency check.
- Use calendar `date` values for a transaction's date, not timestamps, so totals don't
  shift across time zones.

## Next.js

- This version differs from older conventions, for example using `proxy.ts` rather than
  middleware. Check the relevant guide in `node_modules/next/dist/docs/` before using a
  Next.js API, and heed deprecation notices.
- Default to Server Components. Add `use client` only when browser interactivity requires
  it.
- `cacheComponents` is on. Follow the bundled docs for wrapping dynamic content in
  `Suspense`.
- Do not use `use cache` for per-user data by default (invariant 9). Shared reference data
  such as exchange rates may be cached.
- Use Server Actions for app mutations. Treat each as a public endpoint, checking auth,
  ownership and input every time.
- Keep Route Handlers focused on a single responsibility: scheduled jobs, file exports and auth
  callbacks (`app/auth/*`, such as the email link handler `app/auth/confirm`).
- Protect pages through `proxy.ts` for redirects, but authorize in the server code that
  reads or changes data.

## Prisma

- Check the docs for the installed Prisma version, as examples online may target an older
  one.
- Use one shared Prisma Client, `db` from `lib/db/client.ts`, marked `server-only`. Only files in
  `lib/db/` may import it or anything in `lib/db/generated/`.
- `lib/db/generated/` is generated by `prisma generate` (also run on `postinstall`). It is
  git-ignored and never edited.
- Keep `prisma`, `@prisma/client` and `@prisma/adapter-pg` on the same exact version. Use stable
  releases only; npm's `latest` tag for `prisma` has pointed at a release candidate.
- The app connects through `DATABASE_URL` (transaction pooler). The Prisma CLI and migrations use
  `DIRECT_URL` (session pooler), set in `prisma.config.ts`. See `architecture.md`.
- Data-layer functions take `userId` as a required argument and filter by it on every read
  and write to user-owned tables.
- Use `Decimal` columns: `@db.Decimal(19, 4)` for money and `@db.Decimal(28, 10)` for
  investment quantities and exchange rates.
- Schema conventions (owner's decision on 2026-11-25, unit 1.5, Question D):
  - Models are PascalCase and singular (`Profile`, `GoalMilestone`); tables are snake_case and plural
    through `@@map` (`profiles`, `goal_milestones`).
  - Fields are camelCase in Prisma, with snake_case columns through `@map` (`preferredCurrency` →
    `preferred_currency`), so raw report queries need no quoted names.
  - Primary keys are `id`, a UUID made by Postgres:
    `@id @default(dbgenerated("gen_random_uuid()")) @db.Uuid`. `profiles.id` is the exception: the auth
    user's ID, with no default.
  - Every user-owned table has `userId String @map("user_id") @db.Uuid`, indexed (`profiles` uses its
    `id`).
  - Timestamps: `createdAt` (`@default(now())`) and `updatedAt` (`@updatedAt`), both
    `@db.Timestamptz(3)`. Calendar dates are `@db.Date`.
  - Currency codes are `@db.Char(3)`, ISO 4217, upper case, from `lib/money/currencies.ts`.
  - Hand-added check constraints are named `<table>_<column>_<rule>`
    (`profiles_preferred_currency_format`).
  - Enums (unit 2.2): a PascalCase Prisma enum with lower-case values, its Postgres type snake_case through
    `@@map` (`TransactionType` → `transaction_type`). Use one only for a short, stable set.
- Data-layer modules live in `lib/db/<table>.ts`, one per table, and return plain values (strings,
  never Prisma objects). Defaults for a missing row live in the data layer or `lib/`, not as database
  defaults, so there is one source.
- Convert `Decimal` values to strings before they leave the data layer.
- Single-row reads and writes on a user-owned table filter on `id` **and** `userId` together
  (`findFirst`, `update` with `where: { id, userId }` and P2025 as "not found", `deleteMany` with a count),
  so another user's row behaves exactly like a missing one (unit 2.2). Check an ID with `z.uuid()` before
  the query.
- Calendar dates (`@db.Date`) are written as `new Date("<YYYY-MM-DD>T00:00:00.000Z")` and read back with
  `toISOString().slice(0, 10)`, so no time zone shifts the day (unit 2.2).
- Change the schema only through Prisma Migrate. Run `migrate dev` only against the
  development Supabase project, and apply changes to production with `migrate deploy`.
- Do not use `db push` on a database with real data, and do not edit a migration that has
  already been applied.
- Every new table's migration enables RLS through hand-added SQL
  (`migrate dev --create-only`), with no public policies.
- Migration workflow: change `schema.prisma`, run `npx prisma migrate dev --create-only --name <name>`,
  add `ALTER TABLE "<table>" ENABLE ROW LEVEL SECURITY;` for each new table, review the SQL, then run
  `npx prisma migrate dev` to apply it to development. Commit the migration folder and
  `prisma/migrations/migration_lock.toml`. Production follows the routine in `architecture.md`.
- Do not use `FORCE ROW LEVEL SECURITY` on app tables. It was only used to test the `prisma` role in
  unit 0.4.
- Do not model or migrate the Supabase `auth` schema.
- Use `$queryRaw` tagged templates for complex report queries. Never use
  `$queryRawUnsafe` or build SQL from strings.

## Styling

- Use the CSS custom property tokens in `ui-context.md`, with no hardcoded hex values (the Google logo's
  brand colours are the only exception; see `ui-context.md`).
- Follow the border radius scale in `ui-context.md`.
- Use Tailwind utilities. Add custom CSS only for token definitions or what utilities can't
  express.
- Build mobile-first, with no horizontal page scroll at phone width.
- Keep interfaces keyboard-accessible, with visible focus states and labeled controls.

## API Routes

- Validate and parse request input before any logic runs.
- Enforce auth and ownership before any mutation.
- Return consistent shapes: `{ data }` on success and `{ error: { code, message } }` on
  failure, with accurate HTTP status codes. Server Actions return the same shape.
- Never expose stack traces, SQL or provider errors to the client.
- Error pages (`app/error.tsx`, `app/global-error.tsx`, and later in-shell ones) use `ErrorStatus` from
  `components/status-page`: they show only the error's `digest` as a reference, never `error.message`
  or a stack, and log nothing in the browser. Type the `error` prop as `unknown`, and recover with
  `retry`, not `reset`.
- Pages that can't find a record, or find another user's, call `notFound()` in both cases.
- Data Server Actions (unit 1.5's `updateProfile` is the first) call `getSignedInUser()` first, then
  validate with a shared Zod schema in `lib/validation/`, then call the data layer with the session's
  user ID. They return `{ data }` or `{ error: { code, message, fieldErrors? } }` with `NOT_SIGNED_IN`,
  `INVALID_INPUT` or a save failure code, and log only the error's `name` and a Prisma `P####` code. The
  shape, `failure()` and `logActionError()` are shared in `lib/actions/result.ts` (unit 2.2); each action
  file keeps its own codes and messages. An action that ends in `redirect()` calls it outside every `try`
  (Next.js throws to redirect).
- A schema whose output feeds the action (as the forms send parsed values) must also accept its own
  output: parsing twice gives the same result (unit 1.5's `null` display name).
- A form schema shows every field error in one submit: a cross-field check uses Zod's `when` option, and
  no field check uses `abort: true`, which would stop the object-level checks (unit 2.2's amount check).
- Scheduled routes live in `app/api/cron/<job>/route.ts`, one per job, each with its own schedule in
  `vercel.json`. They export only `POST` (Schedules' default, never cached), call `authorizeCron` from
  `lib/cron/authorize.ts` before any work, fail closed when `CRON_SECRET` is unset, set
  `Cache-Control: no-store`, and never log secrets or error messages, only an error's name.
- Every step a scheduled route runs is idempotent, since a run can be repeated or skipped.
- `proxy.ts` must not run on, or redirect, `/api/cron/*`; the route's secret check is its authorization.
  Its matcher excludes it.

## Auth

- Use `getCurrentClaims()` from `lib/auth/session.ts` (built on `getClaims()`) to identify the user on
  the server. Never trust `getSession()` on the server. Pages and components read the user only through
  `getCurrentClaims()`, never `supabase.auth.getClaims()` directly: it awaits `io()` first, because
  `getClaims()` reads `Date.now()`, which Cache Components forbids while prerendering an App Shell.
- Create a new Supabase client per request (`createSupabaseServerClient()`); never share one.
- Every Supabase client passes `cookieOptions: sessionCookieOptions(...)` (`lib/auth/cookie-options.ts`),
  so session cookies are `Secure` over HTTPS; `@supabase/ssr`'s defaults leave it off.
- Auth Server Actions validate with the shared schemas in `lib/validation/auth.ts` before calling
  Supabase, and return `{ error: { code, message } }` (plus `fieldErrors` for invalid input).
- Auth messages and redirects never reveal whether an email address has an account.
- Log only an auth error's `name` and Supabase `code` (`logAuthError`), never its message, the email or
  a token.
- Email links redirect only to paths in `lib/auth/redirect.ts`'s allowlist. Build an email link's
  redirect URL with `emailRedirectUrl()` from the request's `Origin` header; never take a URL from form
  input.
- Pages and Server Components get the user through `requireUser()` (`lib/auth/session.ts`), which also
  sends a session that owes its 2FA code to `/two-factor`. Server Actions that read or change user data
  use `getSignedInUser()` and return an error result rather than redirecting; it is `null` until 2FA is
  done (invariant 6). Only auth code (the 2FA step, the reset flow) uses `getCurrentClaims()` directly.
- Whether a user has 2FA comes only from Supabase (`getUser()`, or a sign-in response's `user`), through
  `verifiedTotpFactor()` in `lib/auth/assurance.ts`; never from the session cookie's copy of the user,
  which the browser can edit. When that check fails, treat the session as `needs-2fa` (fail closed).
- 2FA actions check that a factor ID belongs to the user (from `getUser()`) before using it, and a
  verified factor is only removed after a current code. Never log or return codes, setup keys, QR codes,
  `otpauth://` URIs or factor IDs, except the setup key and QR code returned once to the user setting up.
- The 2FA step continues only through `safeTwoFactorNext` (a safe app page, or `/reset-password`).
- Every page is protected unless it is listed in `lib/auth/paths.ts`. A new public page must be added
  there as a guest page or an open page; the proxy's rules and `safeReturnPath` both read those lists.
  `/two-factor` (`TWO_FACTOR_PATH`) is its own kind: shown only in the `needs-2fa` state.
- The proxy redirects only `GET` and `HEAD` requests, and every redirect goes through
  `redirectWithSession` so refreshed session cookies are kept. Never redirect Server Action `POST`s.
- The sign-in return path goes through `safeReturnPath`; never redirect to a `next` value directly.
- Build the Google sign-in return URL with `oauthRedirectUrl()` from the request's `Origin` header; never
  take a URL from form input. `/auth/callback` returns only through `safeReturnPath`, and logs an OAuth
  `error` parameter only through `logProviderError` (a safe code); never log `error_description`.
- Client components don't import `lib/auth/errors.ts` (it pulls Supabase into the browser bundle); a
  page passes any message they need as a prop.
- The `fintrack-reset-pending` cookie (`lib/auth/reset-pending.ts`) only chooses the page for a browser
  that is already signed in; never treat it as proof of anything. Set it on every path to the reset
  check-email page, never only for real accounts.

## Data and Storage

- Relational data and file metadata belong in the database.
- Receipt files belong in the private storage bucket, never in the database.
- Check file type and size on the server: images or PDFs, up to 5 MB.
- Store a transaction's original amount and currency. Do not store converted totals.
- Secrets stay in server-only environment variables, are never committed, and never use the
  `NEXT_PUBLIC_` prefix. This includes `DATABASE_URL`, `DIRECT_URL` and `CRON_SECRET`.
- The only `NEXT_PUBLIC_` variables are `NEXT_PUBLIC_SUPABASE_URL` and
  `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, which are public by design. Never use Supabase's secret key
  (`sb_secret_…`) or `service_role` key in the app.
- Do not log financial data, tokens or personal details.

## Testing

- Unit test all logic in `lib/money` and `lib/fx`, recurring schedules, and investment and
  debt calculations.
- Each feature that stores user data has a test proving one user can't read or change another
  user's data.
- Each feature's main flow has a Playwright test.
- Render tests of components use `react-dom/server` in Vitest's `node` environment, as
  `tests/unit/*.test.tsx`; no DOM library.
- Unit tests go in `tests/unit/` and run with `npm test` (`npm run test:watch` to watch). Database
  tests go in `tests/db/` and run with `npm run test:db`. Playwright tests go in `tests/e2e/` and run
  with `npm run test:e2e`, after `npm run build`.
- Run tests through the npm scripts, not bare `vitest`, which runs both Vitest projects and stops at the
  database setup's "run on CI" message.
- Database tests run only on CI's throwaway Postgres. There is no local test env file, and
  `tests/db/setup.ts` refuses any Supabase host. They may create data freely, since the database is
  discarded after each run.
- Tests don't import Prisma Client directly. The RLS test uses `pg` against the system catalogs.
- CI logs are public, so tests never print connection details or personal data.
- Tests import `describe`, `test` and `expect` from `vitest` explicitly, with no globals.
- CI must pass before merging into `main`.

## File Organization

- `app/` — Routes, layouts and feature Server Actions.
- `components/ui/` — Generated shadcn/ui components.
- `components/app-shell/` — The sidebar, phone top bar, page header and account area (the user menu,
  rendered once by the app layout beside the page header) shared by signed-in pages.
- `components/auth/` — The auth layout's brand panel and illustration, the auth forms and their shared
  pieces (`use-auth-form.ts`, `form-field.tsx`, `styles.ts`), the Google button (`google-sign-in.tsx`,
  `google-logo.tsx`), the status shared by the email form and the Google button
  (`auth-form-status.tsx`), and the 2FA step's form and code field (`two-factor-form.tsx`,
  `code-input.tsx`, unit 1.4).
- `components/profile/` — The Profile page's Personal details card and form (`profile-card.tsx`,
  `profile-form.tsx`, unit 1.5).
- `components/settings/` — The Settings page's sections: Security (`security-card.tsx`) with the 2FA row,
  setup panel and turn-off dialog (`two-factor-section.tsx`, `two-factor-code-form.tsx`), unit 1.4.
- `proxy.ts` — Session refresh for every page request, plus the route rules (unit 1.2a).
- `components/transactions/` — The Transactions list (`transaction-list.tsx`, `transaction-list-view.tsx`),
  the status line (`done-status.tsx`), the form and its card (`transaction-form.tsx`,
  `transaction-form-card.tsx`), the type control and the delete dialog (unit 2.2).
- `lib/actions/` — The data actions' shared result shape and safe logging (`result.ts`, unit 2.2).
- `components/money/` — The Amount and Currency fields (`money-fields.tsx`, unit 2.1). The select style
  they share with the Profile form is `selectClass` in `components/auth/styles.ts`.
- `components/status-page/` — The 404 and error pages' shared layout (`StatusPage`) and error content
  (`ErrorStatus`).
- `components/<feature>/` — Feature-specific components.
- `hooks/` — Generated shadcn/ui hooks, such as `use-mobile.ts`. Not hand-edited.
- `lib/utils.ts` — Generated `cn()` helper. Not hand-edited.
- `lib/` — Server and shared logic: `db`, `auth`, `cron`, `money`, `fx`, `notifications`.
- `lib/cron/` — The `CRON_SECRET` check for scheduled routes.
- `lib/auth/` — Supabase clients, session helpers (`getCurrentClaims`, `getSessionStatus`,
  `requireUser`, `getSignedInUser`, `getTwoFactorStatus`), the session state (`assurance.ts`), auth error
  mapping, the redirect allowlist and return path checks, and the proxy's route rules.
- `lib/validation/` — Zod schemas shared by forms and Server Actions (`auth.ts`, `profile.ts`, `money.ts`,
  `transaction.ts`).
- `prisma/` — Prisma schema and migrations.
- `prisma.config.ts` — Prisma CLI config: schema and migrations paths, and the migration connection.
- `.env.example` — The required environment variables, with placeholder values only.
- `vercel.json` — Vercel config: function region, schedules and which branches deploy.
- `tests/unit/` — Vitest unit tests, with no database.
- `tests/db/` — Vitest database tests, run only on CI's throwaway Postgres. They reach tables through the
  `lib/db` modules (with `vi.mock("server-only")`), and use `pg` only for raw constraint and catalog
  checks; each test uses fresh random user IDs. `profiles.test.ts` (unit 1.5) holds the first cross-user
  test, `transactions.test.ts` (unit 2.2) the second.
- `tests/e2e/` — Playwright tests. Signed-in tests use the session saved by `auth.setup.ts` (in the
  git-ignored `tests/e2e/.auth/`) and skip when `E2E_USER_EMAIL` and `E2E_USER_PASSWORD` aren't set,
  as in CI. `E2E_PORT` runs them beside a dev server on port 3000. One development account serves every
  test, and its 2FA stays off; the owner's own account is kept for hand checks. The 2FA flow test
  (`two-factor-flow.spec.ts`, unit 1.4) turns 2FA on and off on it with codes from `tests/e2e/totp.ts`,
  records no trace, screenshot or video, and runs in its own Playwright project after all the others,
  because turning 2FA on signs out the account's other sessions.
- `vitest.config.mts`, `playwright.config.ts` — Test runner config.
- `.github/workflows/` — CI.
- `context/` — Project specifications and progress tracking.
- `context/feature-specs/` — One spec per feature unit, written before the unit is built.
