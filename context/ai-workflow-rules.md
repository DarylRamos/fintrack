# AI Workflow Rules

## Approach

Build this project incrementally using a spec-driven workflow. Context files define what to
build, how to build it, and the current state of progress. Always implement against these
specs; do not infer or invent behavior from scratch.

Phase 0 does not start until the project owner gives the go signal. See
`progress-tracker.md` for current status.

## Feature Specs

Every unit needs a spec before anything is built. This is a standing rule from the owner.

- Create it at `context/feature-specs/<phase>.<unit>-<description>.md`, such as
  `context/feature-specs/0.1-theme-tokens-fonts-metadata.md`.
- Use the same structure: Goal, then Implementation, then other necessary details, and end with
  a Check When Done list to validate the executed steps.
- Do not start building a unit until the owner has approved its spec.
- When the unit is done, tick its checks and set its status to Complete.

## Scoping Rules

- Work on one feature unit at a time
- Prefer small, verifiable increments over large speculative changes
- Do not combine unrelated system boundaries in a single implementation step

## When to Split Work

Split an implementation step if it combines:

- UI changes and scheduled job changes
- Database schema changes and unrelated feature work
- Multiple unrelated Server Actions or Route Handlers
- A new external provider and the features that consume it
- Behavior not clearly defined in the context files

If a change cannot be verified end to end quickly, the scope is too broad; split it.

## Handling Missing Requirements

- Do not invent product behavior not defined in the context files
- If a requirement is ambiguous, resolve it in the relevant context file before implementing
- If a requirement is missing, add it as an open question in `progress-tracker.md` before
  continuing
- Do not add paid services, or features listed as out of scope in `project-overview.md`,
  without the owner's approval

## UI Work

- Follow `ui-context.md` for all UI work.
- Use the UI UX Pro Max skill (`.claude/skills/ui-ux-pro-max`) for UI design work.
- Keep agent files in `.claude/` and project instructions in `CLAUDE.md`. Do not add `.agents/`.
- `ui-context.md` takes priority over the skill's suggestions. If a suggestion is worth
  adopting, update `ui-context.md` first.

## Protected Files

Do not modify the following unless explicitly instructed:

- `components/ui/*` — generated UI library components
- `hooks/use-mobile.ts` and `lib/utils.ts` — generated by the shadcn CLI
- `prisma/migrations/*` that have already been applied — add a new migration instead
- `node_modules/` and any third-party library internals
- Installed third-party skill files
- `Functional Design.docx`, `High-level Requirements.docx` and `User Story.docx` — source
  documents
- `.env*` files — ask the owner to add or change secrets

## Keeping Docs in Sync

Update the relevant context file whenever implementation changes:

- System architecture or boundaries
- Storage model decisions
- Code conventions or standards
- Feature scope
- UI tokens or patterns

## Before Moving to the Next Unit

1. The current unit works end to end within its defined scope
2. No invariant defined in `architecture.md` was violated
3. `progress-tracker.md` reflects the completed work
4. `npm run build` and `npm run lint` pass
5. Unit tests pass, once the test setup exists in Phase 0
6. New user-data features have a cross-user access test
7. The unit's main flow passes in Playwright, where it has a user-facing flow
