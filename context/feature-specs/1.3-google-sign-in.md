## Goal

Today a user can only sign up and sign in with email and password. After this unit:

- The sign-in and sign-up pages show an "or" divider and a **Continue with Google** button.
- Pressing it sends the browser to Google; after the user agrees, it returns to FinTrack signed in. The
  first time, Supabase creates the account; there is no separate "sign up with Google" flow.
- If the sign-in started from `/sign-in?next=/budgets`, the user lands on `/budgets`, checked with
  `safeReturnPath` as in unit 1.2a.
- If the user cancels, or Google or Supabase refuses, the user is back on the sign-in page with one short
  message, and nothing reveals whether an account exists.
- A Google account with the same, verified email as an existing FinTrack account signs in to that
  account (Supabase's automatic identity linking). A different email is a different FinTrack account.

2FA for every sign-in method stays in unit 1.4.

## How the Flow Works

The project's pattern stays the same: every auth step is a Server Action or a Route Handler, and there is
no browser Supabase client (architecture: Auth and Access Model).

1. The button submits a form to a new Server Action, `signInWithGoogle({ next })`.
2. The action validates the input with Zod, builds the return URL from the request's `Origin` header
   (`<origin>/auth/callback?next=<safe path>`), and calls `supabase.auth.signInWithOAuth({ provider:
   "google", options: { redirectTo, skipBrowserRedirect: true } })`. This call doesn't contact Supabase:
   it builds the authorize URL and writes the PKCE code verifier cookie through the server client's
   `setAll`.
3. The action calls `redirect(data.url)`. The browser goes to Supabase's `/auth/v1/authorize`, then to
   Google, then back to Supabase's own callback (`https://<project-ref>.supabase.co/auth/v1/callback`),
   then to FinTrack's `/auth/callback?code=…`.
4. The new Route Handler `app/auth/callback/route.ts` exchanges the `code` with
   `exchangeCodeForSession` (which needs the verifier cookie from step 2, so the same browser), and
   redirects to `safeReturnPath(next)`. The session cookies go out with that redirect.
5. On any failure it redirects to `/sign-in?error=google`, and the sign-in form shows the message.

Notes:

- **Why Google's console is needed:** Google only shares a person's identity with apps registered with
  it, through a client ID and secret. Supabase runs the flow with FinTrack's own client; it has none to
  lend.
- **Google never sees FinTrack's URL.** Google only knows Supabase's callback URL. The FinTrack URL is
  checked by Supabase against the project's **Redirect URLs**, which already allow
  `http://localhost:3000/**` and `https://fintrack-kappa-blush.vercel.app/**`. **No Redirect URL change is
  needed** (1.1a's note expected one; the wildcard from its Manual Task 2 already covers `/auth/callback`).
- **No new environment variables.** The Google client secret is entered in each Supabase project's
  dashboard only, never in `.env.local`, Vercel or GitHub.
- **`/auth/callback` is a new route, not a reuse of `/auth/confirm`.** `/auth/confirm` is for email links:
  its `next` has a two-item allowlist and its failure page talks about email links and the reset cookie.
  Keeping them apart keeps each one small.
- **The proxy needs no change.** `/auth/*` is already passed through (unit 1.2a), and `safeReturnPath`
  already refuses `/auth/...`, so the callback can't become a return target.
- **One provider, no provider abstraction.** The action and callback are written for Google only
  (code-standards: no abstraction before a second real use). The callback itself isn't Google-specific,
  so a later provider would only add an action and a button.

## Errors

| What happened | Where it is seen | Result |
| --- | --- | --- |
| Bad input to the action | Action | `{ error: { code: "INVALID_INPUT" } }`; the form shows the generic message |
| `Origin` missing or not http(s) | Action | `AUTH_FAILED`, Supabase not called |
| `signInWithOAuth` returns an error or no URL | Action | `AUTH_FAILED`, logged with `logAuthError` |
| User cancels at Google | Callback gets `?error=access_denied` | `/sign-in?error=google` |
| Any other error Supabase passes back | Callback gets Supabase's `?error=…` | `/sign-in?error=google` |
| No `code`, an overlong `code` (over 512 characters), or the exchange fails (for example, another browser) | Callback | `/sign-in?error=google` |

- **One message for every callback failure:** "Google sign-in didn't finish. Try again, or use your email
  and password." It never names a reason, so it never reveals an account.
- **Logging:** the callback logs only `[auth] oauthCallback failed: <name> (<code>)` through
  `logAuthError` for a failed exchange. For an `error` parameter it logs the parameter only if it matches
  `^[a-z_]{1,64}$` (for example `access_denied`), never `error_description`, which can contain personal
  details.
- **The message is read in the browser** (Question A), the same way `SignInForm` reads `next` at submit
  time, so `/sign-in` stays fully static. On mount, if the URL has `error=google`, the form shows the
  message in its existing `FormAlert` (announced and focused), then removes the parameter from the
  address bar with `history.replaceState`, so a reload doesn't show it again. Any other `error` value is
  ignored. Supabase sometimes adds an `#error=…` fragment; the browser keeps it across the callback's
  redirect, and the auth layout's `ClearAuthErrorHash` (unit 1.1b) already removes it.

## Account Linking and Identities

- Supabase links identities with the **same email** to one user automatically, and doesn't link to an
  unverified email (to prevent pre-account takeover). FinTrack adds no code for this and offers no manual
  linking or unlinking screen in this unit.
- The user menu shows the first letter of the user's email, which every Google account has.
- The name and avatar Google shares, which Supabase stores in `user_metadata`, are not shown or copied
  anywhere. Display names arrive with the profile in unit 1.5.
- Signing out works the same for every method (this device only). It doesn't sign the user out of Google.

## Decisions

- **Email and Google only; Facebook removed:** owner's decision on 2026-11-18. Facebook would have needed
  a Meta app and, to open it to anyone, a privacy policy and Meta's review, while Google covers the same
  need. `project-overview.md`, `architecture.md`, `ui-context.md` and `progress-tracker.md` were updated
  the same day.
- **Server Action plus Route Handler, no browser Supabase client:** same as every other auth step.
- **A separate `/auth/callback`:** email links and OAuth have different `next` rules and failure pages.
- **Return path through `safeReturnPath` twice:** once when the action builds `redirectTo`, again in the
  callback, since the callback's query string can be edited by anyone.
- **Automatic linking by email, no linking UI:** Supabase's default, and enough for a single owner.
- **The Google secret only in Supabase:** FinTrack's code and hosting never hold it.
- **A full-width labelled button:** with one provider, instead of the round icon buttons planned for two.

## Rules to Follow

- Follow `architecture.md` and `code-standards.md`, especially the Auth rules: validate input first,
  `getClaims()` through `getCurrentClaims()` where a user is needed, never `getSession()` on the server,
  no account enumeration, log only an error's `name` and `code`.
- Don't log or print tokens, codes, cookies, `next` values, email addresses, error descriptions or the
  test account's credentials.
- `proxy.ts` and its matcher are unchanged; `/api/cron/*` is never touched.
- No schema or migration change. Never run anything against production. Don't edit `.env*` or
  `components/ui/*` (add shadcn components through the CLI if any are needed).
- Don't commit until the owner says so.
