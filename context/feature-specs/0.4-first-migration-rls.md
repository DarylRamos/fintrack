# 0.4 First Migration with RLS and the Prisma Role's RLS Behavior

**Phase:** 0, Foundation
**Status:** Complete (approved and completed on 2026-11-13)
**Depends on:** Unit 0.3 (Supabase projects, Prisma setup and connection strings)

## Goal

Set up FinTrack's migration workflow and its RLS rule before any feature table exists. When this unit is
done:

- the first Prisma migration is applied to both Supabase projects, through `migrate dev` on development
  and `migrate deploy` on production;
- every table in `public` has RLS enabled, including Prisma's own `_prisma_migrations` table
  (invariant 4);
- a test on the development database confirms that the `prisma` role bypasses RLS, so the data layer's
  `user_id` filters, not RLS, are what limit Prisma queries;
- the Data API question from unit 0.3 is answered and acted on;
- the production migration routine and the schema conventions are written down for later units.

## Scope

**In scope**

- The first migration, created with `migrate dev --create-only`, holding hand-written SQL only
- `prisma/migrations/migration_lock.toml`, created by Prisma
- Applying the migration to development (agent) and production (owner)
- A temporary RLS test script in the scratchpad, run against development only, never committed
- Checking which roles can access tables created by the `prisma` role
- The Supabase Data API decision (see Decisions), and the owner turning it off if approved
- Doc updates in `architecture.md`, `code-standards.md` and `progress-tracker.md`

**Out of scope**

- Any Prisma model or application table, including `profiles` (Phase 1, once its fields are defined)
- Data-layer functions and the cross-user access test pattern (the first feature that stores user data)
- Vitest, Playwright, CI, and an automated "every table has RLS" test (unit 0.5)
- Running migrations from Vercel's build (unit 0.6 decides this)
- Seed data
- Supabase Auth, Storage, and their packages (Phases 1 and 2)
- Any change to app code, `next.config.ts` or dependencies

## Implementation

Do not start until the owner approves this spec and confirms Manual Task 1.

### 1. Check the docs

1. Read the Prisma 7 docs on customizing migrations (empty migrations with `--create-only`), the shadow
   database, and `migrate deploy`. Examples online may target Prisma 6 or the Prisma 8 release candidate.
2. Read Supabase's current docs on the Data API: how to turn it off, and confirm that Supabase Auth
   (`/auth/v1`) and Storage (`/storage/v1`) keep working without it. Tell the owner where the toggle is
   (Manual Task 2). If the docs say Auth or Storage needs it, stop and report.
3. Read Supabase's docs on RLS and the default grants given to `anon` and `authenticated` in `public`.

### 2. Create the migration

1. Run `npx prisma migrate dev --create-only --name init`. With no models, Prisma creates an empty
   migration folder. `migrate dev` uses a shadow database, which the `prisma` role can create because it
   has `createdb`.
   - If creating the shadow database fails through the session pooler, stop and report. Do not set
     `shadowDatabaseUrl` to the production project, and do not try other workarounds without approval.
2. Write `migration.sql`:

   ```sql
   -- Invariant 4: RLS is on for every table in public, with no policies.
   -- Prisma creates _prisma_migrations itself, not from a model, so this migration enables RLS on it.
   -- The guard keeps the migration valid in the shadow database, where the table may not exist.
   DO $$
   BEGIN
     IF to_regclass('public._prisma_migrations') IS NOT NULL THEN
       ALTER TABLE public._prisma_migrations ENABLE ROW LEVEL SECURITY;
     END IF;
   END
   $$;
   ```

   If step 1 shows the guard is unnecessary, keep it anyway: it costs nothing and covers both cases.

### 3. Apply it to development

1. Run `npx prisma migrate dev`. It applies `init` and reports the database is in sync.
2. Run `npx prisma migrate status`. It must report one applied migration and no drift.
3. Run `npx prisma generate` and `npx prisma validate` to confirm nothing else changed.

### 4. Test the `prisma` role's RLS behavior

Write a temporary Node script in the scratchpad. It loads env files with `loadEnvConfig(process.cwd(),
true)` from `@next/env`, connects with `pg` through `DIRECT_URL` (development), and loads both packages
from the project's `node_modules` with `createRequire`. It prints booleans, counts and role names only,
never a connection string, host or password.

In **one transaction that ends with `ROLLBACK`**, so nothing is left behind, it:

1. creates `public.rls_probe (id int primary key)`, enables RLS **and** `FORCE ROW LEVEL SECURITY`, with
   no policies (`FORCE` makes RLS apply to the table owner too, so only `BYPASSRLS` can let `prisma` in);
2. inserts one row, then counts the rows. Expected: the insert works and the count is 1, proving
   `BYPASSRLS` works in practice;
3. reads `current_user` and `rolbypassrls` from `pg_roles`. Expected: `prisma`, `true`;
4. checks `has_table_privilege` for `anon` and `authenticated` on `rls_probe` (`select`, `insert`,
   `update`, `delete`). This shows whether Supabase's default grants reach tables the `prisma` role
   creates. Record the result either way. With RLS on and no policies, those roles see no rows even when
   they have grants.

Then, outside the transaction, it checks the real state:

5. lists every table in `public` with `relrowsecurity = false`. Expected: none;
6. checks `has_table_privilege` for `anon` and `authenticated` on `_prisma_migrations`, and records it.

Run it, record the results in Notes, and delete the script.

If step 2 or 3 fails, stop and report: the RLS model in `architecture.md` would need to change.

## Decisions

- **No application table in the first migration:** `profiles` is the natural first table, but its
  fields (preferred currency, notification preferences) belong to Phase 1. Creating it now would mean
  inventing them early, which `ai-workflow-rules.md` rules out. The migration enables RLS on
  `_prisma_migrations` instead, which is a real requirement of invariant 4 and proves the whole
  `--create-only`, `migrate dev` and `migrate deploy` workflow on both projects.
- **RLS behavior is tested in a rolled-back transaction:** it uses a real table and real roles on the
  development database, but leaves nothing in the schema or the migration history.
- **Turn the Supabase Data API off in both projects (approved by the owner on 2026-11-13):** only
  Prisma reads the database, so the Data API is unused surface. Turning it off adds a second barrier
  behind RLS. It can be turned back on if a later phase needs it.
- **The production migration is applied now, by the owner:** it keeps both projects on the same
  migration history from the first migration, and proves the production routine before real data
  exists. Unit 0.6 decides whether Vercel's build should ever run `migrate deploy`; the proposal is that
  it shouldn't.
- **Schema naming conventions are deferred to Phase 1:** owner's decision on 2026-11-13. They're
  decided with the first application table.
