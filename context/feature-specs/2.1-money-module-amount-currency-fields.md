# 2.1 Money Module, with Amount and Currency Fields

**Phase:** 2, Transactions (the first Phase 2 item)
**Status:** Built (2026-11-27). Approved on 2026-11-27 with the recommended answers to Questions A to E.
Local checks pass; not committed yet, so CI hasn't run. See Implementation Notes.
**Depends on:** Unit 1.5 (`lib/money/currencies.ts`, the shared form pieces, the native select's style), unit
0.5 (Vitest render tests).

## Goal

Phase 2 stores and shows money for the first time. Before the transactions table exists (unit 2.2), this
unit settles **how an amount is entered, checked, stored and shown**, once, so every later feature (budgets,
goals, investments, debts, reports) reuses it:

- **Entering:** what a user may type in an amount field ("1,234.50", "1234.5", ".5") and what is refused
  ("1.234,50", "-20", "1e5", "$20", too many decimal places, zero, too large), with one clear message each.
- **Checking:** one shared Zod schema for an amount and its currency, used by forms in the browser and by
  Server Actions on the server (invariant 5).
- **Storing:** one canonical decimal string ("1234.50") that goes into `numeric(19, 4)` exactly, never
  through a JavaScript `number` (invariant 1).
- **Showing:** one `formatMoney` function on `Intl.NumberFormat`, with each currency's decimal places fixed
  in the app, so the server and the browser always print the same text.
- **The fields:** an **Amount** input and a **Currency** picker, as one reusable form component, ready for
  unit 2.2's transaction form (Question A).

No table, migration, page, Server Action or provider call. Nothing converts between currencies yet
(Phase 3).

## Design

### Decimal places per currency (Question D)

`lib/money/currencies.ts` gains a fixed table, `CURRENCY_DECIMALS`, and `currencyDecimals(code)`. It sets how
many decimal places an amount may have when it is typed and how many are shown.

Node 24 (ICU 78, CLDR 48) formats 25 of the 30 currencies with 2 decimal places and these 5 with none: **HUF,
IDR, ISK, JPY, KRW**. ISO 4217 gives HUF and IDR 2 decimal places, but they are not used in practice, and
`Intl` doesn't show them. **Recommended:** the table matches what `Intl` shows (0 for those 5, 2 for the
rest), so what you type is exactly what you see. The table is fixed in the app, not read from `Intl` at run
time, so a browser with different locale data can't disagree with the server. It is always passed to `Intl`
as `minimumFractionDigits` and `maximumFractionDigits`.

### The canonical amount string

An amount crosses between browser, server and database as a **decimal string** in one form:

- ASCII digits only, no grouping, no sign, no leading zeros (except a single `0` before the point);
- exactly the currency's decimal places: `"1234.50"` (SGD), `"1500"` (JPY), `"0.05"` (USD).

`numeric(19, 4)` stores it exactly (as `1234.5000`). Unit 2.2's data layer turns Prisma's `Decimal` back into
this form with the currency's decimal places (`decimal.toFixed(currencyDecimals(currency))`), so pages never
see `"1234.5000"`.

### What an amount may be (Question C)

- **Above 0.** A transaction's direction (income or expense) is its own field in unit 2.2, so amounts are
  always positive; a minus sign is refused with a message that says so.
- **At most 999,999,999,999** (12 digits before the point) in any currency. `numeric(19, 4)` allows 15;
  the 3 spare digits leave room for sums in Postgres and Phase 3's conversions.
- **At most the currency's decimal places.** Extra places are refused, not rounded, so nothing changes
  without the user seeing it.

### What a user may type

`parseAmountInput(text, currency)` in `lib/money/amount.ts` (new). It does string work only (no arithmetic,
so no decimal library is needed in this unit; Question B):

| Typed | SGD result | JPY result |
| --- | --- | --- |
| `1234.5`, ` 1234.50 `, `1,234.50` | `"1234.50"` | refused: decimal places |
| `1,234` | `"1234.00"` | `"1234"` |
| `.5`, `0.5`, `00.50` | `"0.50"` | refused: decimal places |
| `20.` | `"20.00"` | `"20"` |
| `1.234,50`, `1234,50`, `12,34` | refused: format (commas group thousands; the point marks decimals) | same |
| `-20`, `+20` | refused: sign | same |
| `1e5`, `$20`, `20 SGD`, `1 234`, `٣٤` (non-ASCII digits) | refused: format | same |
| `0`, `0.00` | refused: zero | same |
| `1,000,000,000,000` | refused: too large | same |
| empty or spaces | refused: empty | same |

- Leading and trailing spaces are trimmed. Commas are accepted only as correct thousands groups (`1,234,567`),
  never after the point. Input longer than 32 characters is refused as a format error.
- The result is `{ ok: true, amount }` or `{ ok: false, reason }`, where `reason` is `empty`, `format`,
  `sign`, `decimals`, `zero` or `too-large`. Messages live in the Zod schema, not here.
- Only English formats, as the app is English-only. Regional input formats (such as `1.234,50`) are Phase 14.

### The shared schema

`lib/validation/money.ts` (new; no secrets, not server-only):

- `currencySchema`: one of `SUPPORTED_CURRENCIES` ("Choose a currency from the list."). The Profile schema's
  `preferredCurrencySchema` becomes this one, with the same message, so there is one currency rule.
- `moneySchema`: `{ amount: string, currency }`. The currency is checked first; then the amount is parsed for
  that currency and **replaced by its canonical string**. Errors are reported on `amount`:

| Reason | Message (SGD; JPY in brackets where different) |
| --- | --- |
| `empty` | "Enter an amount." |
| `format` | "Enter a number, such as 1,234.50." ("…such as 1,234.") |
| `sign` | "Enter the amount without a sign." |
| `decimals` | "SGD amounts have at most 2 decimal places." ("JPY amounts have no decimal places.") |
| `zero` | "Enter an amount above 0." |
| `too-large` | "Enter an amount up to 999,999,999,999." |

- It accepts its own output: parsing `"1234.50"` again gives `"1234.50"` (`code-standards.md`, unit 1.5's
  rule).
- Unit 2.2's transaction schema uses it as `amount` and `currency` fields.

### Showing amounts

`formatMoney(amount, currency)` in `lib/money/format.ts` (new):

- `Intl.NumberFormat("en-US", { style: "currency", currency, currencyDisplay: "symbol", minimumFractionDigits,
  maximumFractionDigits })` with the table's decimal places. The **locale is fixed** at `en-US` until
  Phase 14's regional formats, so every page prints the same way.
- It formats the **string** itself (`Intl.NumberFormat.format` takes a decimal string exactly; Node 24 and
  current browsers support it), never `Number(amount)`. Checked on Node 24: `"999999999999.99"` prints
  `$999,999,999,999.99`.
- It accepts a canonical amount with an optional leading minus (for later net figures and for expenses,
  which show a minus sign), and throws on anything else: that is a programming error, not user input.
- Symbols (Question E): `Intl`'s own, which tell look-alike dollars apart: `$` (USD), `A$`, `CA$`, `NZ$`,
  `HK$`, `MX$`, `€`, `£`, `¥` (JPY), `CN¥`, `₩`, `₹`, `₪`, `₱`, `R$`; the other 15 show their code, such as
  `SGD 1,234.50` and `HUF 1,235`. An expense reads `-SGD 45.00`.
- `amountPlaceholder(currency)`: `"0.00"`, or `"0"` for currencies with no decimal places.
- Pages wrap amounts in `tabular-nums`, per `ui-context.md`. No display component is added until a page needs
  one (unit 2.4's history).

### The fields (Question A)

`components/money/money-fields.tsx` (new, a client component): **Amount** and **Currency**, two labelled
fields built on `FormField`, for a react-hook-form form.

- **Amount:** the standard input (`--bg-muted`, `rounded-md`, `h-11`, `text-base` on phones, `md:text-sm`),
  `type="text"`, `inputMode="decimal"` (phones show a number pad), `autoComplete="off"`, `tabular-nums`,
  placeholder from `amountPlaceholder`. It is not reformatted while typing or on blur; what was typed stays,
  and the schema accepts grouped and ungrouped numbers.
- **Currency:** the Profile page's `NativeSelect` style (its class moves from `profile-form.tsx` to
  `components/auth/styles.ts`, shared by both), options "SGD – Singapore Dollar", sorted by code. The form
  chooses the starting value; unit 2.2 starts with the preferred currency.
- Changing the currency checks the amount again once the form has been submitted, so "12.50" shows the JPY
  decimal-places message at once after switching to JPY.
- **Layout:** one column on phones (Amount, then Currency); side by side from `sm` up, Amount wider
  (`sm:grid-cols-[1fr_14rem]`). No horizontal scroll at 375px.
- Errors appear under each field (`aria-invalid`, `aria-describedby`), as every FinTrack form.
- Its first page and browser test come with unit 2.2's transaction form; here it has render tests only.

## Questions for the Owner

Answered: **A to E, the recommended options** (2026-11-27).

- **A. Build the amount and currency fields now, or with the transaction form?** **Recommended: now**, as one
  component with render tests, as the Phase 2 list names them ("Money module, with amount and currency
  fields"). It keeps unit 2.2 (table, migration, three actions, form, history placeholder, in-shell error
  pages) smaller. Its browser test waits for 2.2, since no page shows it yet. Alternative: this unit is logic
  only (`lib/money` and the schema), and 2.2 builds the fields.
- **B. A decimal library?** **Recommended: none in this unit.** Parsing, checking and formatting need no
  arithmetic: they work on strings, and `Intl` formats decimal strings exactly. Sums will run in Postgres on
  `numeric`. Phase 3's conversion (amount × rate, then rounding) is the first real arithmetic, and picks a
  library then (likely `decimal.js`, the same library Prisma's `Decimal` is built on). Alternative: add
  `decimal.js` now with add, subtract and compare helpers.
- **C. Limits.** **Recommended: amounts above 0, up to 999,999,999,999, always positive** (direction is
  income or expense in 2.2). Alternatives: allow 0 (for example a free item), or a lower cap such as
  999,999,999.
- **D. Decimal places.** **Recommended: as `Intl` shows them**: none for HUF, IDR, ISK, JPY and KRW, 2 for
  the other 25. Alternative: ISO 4217 (2 for HUF and IDR too), shown as "HUF 1,234.00".
- **E. Currency symbols.** **Recommended: `Intl`'s standard symbols** (`$1,234.50`, `€1,234.50`,
  `SGD 1,234.50`), the familiar form. Alternative: always the code (`USD 1,234.50`, `EUR 1,234.50`), which
  looks the same for every currency and never shows a lone `$` beside other dollars.

## Decisions

- **Amounts are strings everywhere outside the database:** one canonical form, checked by one schema, so no
  value passes through a `number`.
- **Refuse, never round, user input:** extra decimal places are an error, so the stored amount is exactly
  what was typed.
- **Decimal places fixed in the app:** the server and browser never disagree, whatever locale data a browser
  has.
- **Positive amounts; direction is a separate field:** budgets, reports and alerts can sum amounts by type
  without checking signs.

## Rules to Follow

- Follow `architecture.md` and `code-standards.md`: no `number` for money, no Prisma outside `lib/db`, Zod
  before any logic.
- Never log amounts or other financial data, including in tests' output and CI's public logs.
- Don't edit `components/ui/*` or `.env*`; no new dependency without the owner's approval (Question B).
- Don't commit until the owner says so.

## Implementation Notes (2026-11-27)

- Built as specified, with the differences below. No database, Prisma, proxy, auth, cron, `vercel.json`,
  Supabase, Vercel or env change, and no new dependency.
- **Step 1 findings:**
  - MDN: `format()` "will use the exact value that the string represents". The compatibility table didn't
    load; engines on the older rule convert the string to a number first, which still prints any amount
    up to the 12-digit cap with 2 decimals (14 significant digits) correctly. Pages mostly format on the
    server (Node 24) anyway.
  - All 30 codes' decimal places and symbols on Node 24 are as the spec lists.
  - **`Intl` puts a no-break space (U+00A0)** between a code and the number (`SGD 1,234.50`), so they never
    wrap apart. Tests compare with ` `.
  - Zod 4.6.7: a `.transform` on the object can add an issue at `["amount"]` and return `z.NEVER`; it runs
    only when every field passed, so an invalid currency adds no amount error. react-hook-form's
    `useForm({ errors })` lets the render test show errors.
  - TypeScript's `Intl.NumberFormat.format` takes `Intl.StringNumericLiteral`, so no `number` cast is
    needed.
- **Composing the schema:** besides `moneySchema`, `lib/validation/money.ts` exports `moneyShape` and
  `withCanonicalAmount`, so unit 2.2's transaction schema can be
  `z.object({ ...moneyShape, … }).transform(withCanonicalAmount)` (a transformed object can't be
  `.extend`ed). **For 2.2:** the amount check runs only once the other fields pass, so an amount error
  appears after the other fields are fixed. 2.2 decides whether that's good enough.
- **Order of checks:** zero is checked before decimal places, so "0.00" in JPY reads "Enter an amount
  above 0." (the spec's table), not the decimal-places message.
- **`MoneyFields`** takes the whole form (`form`, `idPrefix`) for fields named `amount` and `currency`, so
  it can watch the currency (for the placeholder) and re-check the amount when the currency changes after
  a submit (`trigger`).
- **The 32-character limit** counts the trimmed text.
- **Visual check:** a temporary signed-in page and a temporary Playwright script on a production build
  (port 3100, the development test account), at 375, 768 and 1440px, light and dark: the fields were empty,
  then submitted, then switched to JPY. The decimal-places error appeared at once and cleared on switching
  back, with no horizontal scroll. The page, script and screenshots were deleted, and the build was rerun
  without them. In a narrow container (about 400px at `sm`), the fixed 14rem currency column leaves Amount
  the smaller field; unit 2.2's form layout should allow for it.
- **Results:**
  - `npm run lint`, `npm run typecheck` and `npm run build` pass.
  - `npm test`: 659 passed (128 new: `money-amount`, `money-format`, `money-validation`, `money-fields`,
    and the decimal places in `currencies`).
  - Playwright on port 3100 with the test account: 136 passed, 16 skipped (unchanged; no new browser test).
