## Goal

Let the owner create an account with email and password, confirm it by email, sign in, sign out, and
reset a forgotten password, on development and on production. When this unit is done:

- the Supabase Auth clients for Next.js are set up in `lib/auth`, using the `@supabase/ssr` cookie
  pattern;
- `proxy.ts` exists and keeps the Supabase session fresh on every page request, but **does not redirect
  anyone yet** (that is unit 1.2);
- the sign-in and sign-up pages follow the 50/50 layout in `ui-context.md`;
- every auth step runs in a Server Action or the one confirm Route Handler, with Zod validation, and
  never tells a visitor whether an email address has an account;
- the signed-in user can see who they are and sign out from a small user menu in the page header;
- the open question "Does sign-in work with the Supabase Data API turned off?" is answered.

No application table is created. `profiles` (name, preferred currency) waits for unit 1.5, so the
schema naming question stays open until then.

## Why the Proxy Starts in This Unit

The roadmap puts `proxy.ts` in unit 1.2. Supabase's server-side guide makes session refresh in the proxy
a requirement, not an option: Server Components can't write cookies, so without the proxy an expired
access token (1 hour by default) is never refreshed and the user is silently signed out. Email sign-in
can't be proven to work across an hour without it.

So this unit adds the proxy with **one** job, refreshing the session. Unit 1.2 then adds the redirects
for signed-out users, the "already signed in" redirects away from `/sign-in`, and the full server-side
session helpers. Until 1.2, the app pages stay reachable while signed out, as they are today; they show
no data, since none exists.

## Amendment (2026-11-16): Default Email Templates and PKCE Links

**Why.** The approved spec changed the Confirm signup and Reset password templates to token-hash links
(Manual Task 4). On the free plan, Supabase locks the templates while its built-in email is used: editing
them needs custom SMTP or the Pro plan. The owner chose **option A** of three:

- **A (chosen):** keep Supabase's default templates and handle the PKCE `code` they produce. Free, no new
  credentials.
- B: custom SMTP through the owner's Gmail (app password). Unlocks templates, but email then reaches
  anyone, which would reverse answer E. Not chosen.
- C: Supabase Pro. Paid, outside the free-tier rule. Not chosen.

**How the default link works.** The default templates link to `{{ .ConfirmationURL }}`, which opens
Supabase's verify endpoint. Supabase checks the token (confirming the email, for sign-up), then redirects
to the `redirect_to` URL the app gave it, adding a one-time `code`. `@supabase/ssr` uses the PKCE flow, so
the call that sent the email (`signUp` or `resetPasswordForEmail`) also stored a code verifier in a cookie,
and `exchangeCodeForSession(code)` turns the code into a session only when that cookie is present.

**What changes:**

1. `signUp` passes `emailRedirectTo` and `requestPasswordReset` passes `redirectTo`, both pointing at
   `/auth/confirm` on the app's own origin, with a fixed `next` (step 5).
2. `/auth/confirm` also accepts `code` and calls `exchangeCodeForSession`. The token-hash path stays, so
   custom templates can be switched on later (with custom SMTP) without a code change (step 6).
3. Each project gets a Redirect URLs entry, because Supabase only redirects to the Site URL or an
   allowlisted URL (Manual Task 2). The templates stay at their defaults (Manual Task 4).
4. The check-email and auth-error pages explain the same-browser limit (step 7).

**Limitation: open the email in the same browser.** The code exchange needs the verifier cookie, so:

- **Sign-up** opened in another browser or device: Supabase has already confirmed the email before the
  exchange fails, so the user lands on `/auth-error`, which tells them to try signing in, and signing in
  works.
- **Password reset** opened in another browser: the link fails, and the user requests a new one in the
  browser they will open it in.

This suits a single owner who usually reads email on the same device. If cross-device links matter later,
adding custom SMTP and the token-hash templates in Manual Task 4 removes the limit with no code change.

### 2. Supabase clients and session helpers (`lib/auth/`)

All files are `server-only`.

1. **`server.ts`:** `createSupabaseServerClient()` wraps `createServerClient` with the
   `cookies()` `getAll`/`setAll` pattern. `setAll` is in a `try`/`catch` because Server Components can't
   set cookies (the proxy covers them). It throws a clear error if either variable is missing.
2. **`proxy-session.ts`:** `refreshSession(request): Promise<NextResponse>` builds the response, wires
   `getAll`/`setAll` to the request and response cookies, applies the cache headers from `setAll`, calls
   `getClaims()` and returns that response. No code runs between creating the client and `getClaims()`.
   It redirects nobody.
3. **`session.ts`:** `getCurrentClaims(): Promise<{ userId: string; email: string } | null>`, from
   `getClaims()`, narrowed with Zod. It is not cached (invariant 9). Unit 1.2 extends this file.
4. **`errors.ts`:** maps Supabase `AuthError` codes to `{ code, message }`. Messages never confirm whether
   an account exists:
   - wrong email or password → `INVALID_CREDENTIALS`: "Email or password is incorrect."
   - email not confirmed → `EMAIL_NOT_CONFIRMED`: "Confirm your email first. Check your inbox for the
     link." (Supabase only returns this after a correct password.)
   - weak password → `WEAK_PASSWORD`, with the rule.
   - same password on reset → `SAME_PASSWORD`: "Choose a password you haven't used here before."
   - rate limits → `RATE_LIMITED`: "Too many attempts. Try again in a few minutes."
   - anything else → `AUTH_FAILED`: "Something went wrong. Try again." The error's `name` and `code` may be
     logged; the message and the email are not.
5. **`redirect.ts`:** `safeNextPath(value)` returns `value` only if it is one of `/dashboard` or
   `/reset-password`, otherwise `/dashboard`. This blocks open redirects through the email link.
   **Amendment:** `emailRedirectUrl(origin, next)` returns `<origin>/auth/confirm?next=<next>` for an
   allowlisted `next`, or `null` when `origin` is missing, doesn't parse as a URL, or isn't `http:` or
   `https:`. It uses the parsed URL's `origin`, so a path or query in the header is dropped. Pure, so it
   is unit-tested directly.

### 3. Validation (`lib/validation/auth.ts`)

Not `server-only`, because the forms import it too. It holds no secrets.

- `email`: trimmed, lowercased, valid email, at most 254 characters.
- `password` (new passwords): 8 to 72 characters, with at least one lowercase letter, one uppercase letter
  and one digit (ASCII, as Supabase checks). Helper text: "At least 8 characters, with an uppercase
  letter, a lowercase letter and a number." Each missing part gets its own error message. Sign-in only checks it's not empty,
  so a rule change never locks out an older password.
- Schemas: `signInSchema`, `signUpSchema` (email, password, confirm password, matching),
  `forgotPasswordSchema`, `resetPasswordSchema` (password, confirm password).

### 5. Server Actions (`app/(auth)/actions.ts`)

Each action parses its input with the Zod schema first, returns `{ error: { code, message } }` on
failure (and field errors where useful), and redirects on success. None trusts a user ID or URL from the
client.

| Action | Supabase call | On success |
| --- | --- | --- |
| `signUp` | `auth.signUp({ email, password, options: { emailRedirectTo } })` | Redirect to `/check-email?reason=sign-up`, **also** when the email already has an account (Supabase returns no error then, by design) |
| `signIn` | `auth.signInWithPassword` | Redirect to `/dashboard` |
| `signOut` | `auth.signOut({ scope: "local" })` | Redirect to `/sign-in` |
| `requestPasswordReset` | `auth.resetPasswordForEmail(email, { redirectTo })` | Redirect to `/check-email?reason=reset`, whether or not the account exists |
| `updatePassword` | `auth.updateUser({ password })`, only if `getCurrentClaims()` returns a user | Redirect to `/dashboard` |

- `signOut` uses the `local` scope, so other devices stay signed in. ("Sign out everywhere" can come with
  Phase 12's security settings.)
- ~~No `emailRedirectTo` or `redirectTo` is passed.~~ **Amendment:** `signUp` passes
  `emailRedirectTo = emailRedirectUrl(origin, "/dashboard")` and `requestPasswordReset` passes
  `redirectTo = emailRedirectUrl(origin, "/reset-password")`.
  - `origin` is the request's `Origin` header, read with `headers()` from `next/headers`. Browsers always
    send it on a Server Action's POST, and Next.js already refuses Server Action requests whose `Origin`
    doesn't match the host. No new environment variable is needed.
  - If `emailRedirectUrl` returns `null`, the action returns `AUTH_FAILED` without calling Supabase.
  - A forged `Origin` can't send a link anywhere unexpected: Supabase only redirects to the Redirect URLs
    allowlist, and anyone forging it only affects the email sent to their own address.
  - The production link only works from `https://fintrack-kappa-blush.vercel.app`. Another Vercel alias
    (such as a deployment's own URL) isn't on the allowlist, so its emails would land on the home page.

### 6. Email link handler (`app/auth/confirm/route.ts`)

Exports only `GET` (email links are plain links):

1. Read `token_hash`, `type`, `code` and `next`.
2. **Token-hash link** (when `token_hash` is present): `type` must be `email` or `recovery`; anything
   else redirects to `/auth-error`. Then `verifyOtp({ type, token_hash })`.
3. **PKCE link (Amendment)** (when `token_hash` is absent and `code` is present): `code` must be a
   non-empty string of at most 512 characters, otherwise `/auth-error`. Then
   `exchangeCodeForSession(code)`. `type` is ignored on this path.
4. Neither `token_hash` nor `code` (including Supabase's own `error` redirect for an expired or used
   link) redirects to `/auth-error`.
5. On a Supabase error, log it with `logAuthError` and redirect to `/auth-error` (no error text in the
   URL). On success, redirect to `safeNextPath(next)`; reset links therefore land on `/reset-password`
   with a fresh session.
6. Responses carry `Cache-Control: no-store`.

`code-standards.md` limits Route Handlers to scheduled jobs and file exports, so this one is added there
as the third allowed kind: auth callbacks (unit 1.3's OAuth callback joins it).

## Decisions

- **Server Actions for every auth step, no browser Supabase client:** the session lives in cookies the
  server writes, the browser bundle never needs the Supabase URL or key, and each action is validated like
  any other public endpoint. A browser client can be added later if a feature needs realtime.
- **PKCE `code` links from the default templates (Amendment; replaces "token-hash links, not PKCE"):**
  token-hash links work on any device but need custom templates, which the free plan locks with
  built-in email. PKCE links need the same browser, which a single owner can live with. The confirm
  route handles both, so custom SMTP can switch to token-hash links later with no code change.
- **Fixed `next` plus an allowlist (Amendment: set by the actions, not the templates):** the actions
  choose `next`, Supabase's Redirect URLs limit the origin, and `safeNextPath` limits the path, so the
  link can't be turned into an open redirect.
- **Origin from the request, not an environment variable (Amendment):** the Server Action's `Origin`
  header is already checked by Next.js and by Supabase's allowlist, and avoids a new variable per
  environment.
- **`getClaims()`, never `getSession()`, on the server:** as Supabase's guide requires.
- **No account enumeration:** sign-up and reset always end on the same check-email page; sign-in has one
  message for a wrong email or password.
- **Sign out of this device only:** the expected behaviour for a plain "Sign out".
- **Proxy refresh only (Question A):** keeps this unit small and leaves all redirect rules to 1.2.
- **No `profiles` table yet:** the header shows the email until 1.5 adds the name.

## Hand-Check Fixes: `Date.now()` Error and Sign-Up Wording (approved 2026-11-16)

**A. "Blocking Route: `Date.now()`" on `/dashboard` and `/reset-password` (checks 10.2.1 and 10.2.5).**

- **Cause:** with Partial Prefetching, Next.js prerenders each route's App Shell with `cookies()`
  resolved. When a session cookie exists, Supabase's `getClaims()` checks the token's expiry with
  `Date.now()`, which Cache Components forbids in a prerender. Signed out, `getClaims()` returns before
  reading the clock, so the agent's signed-out checks never saw it. Every app page was affected, through
  the header's user menu.
- **Fix:** `getCurrentClaims()` calls `await io()` (from `next/cache`) before `getClaims()`. It resolves
  at once during a request and suspends during prerendering, so the session read streams in behind the
  existing `Suspense`. The bundled docs prefer `io()` over `connection()`, which would also block
  prefetches. Not chosen: `use cache: private` (caches per-user data, against invariant 9, and could
  keep showing a session after it expired).
- **The user menu moves into the app layout:** with `io()`, a menu inside each page's header would be
  rebuilt after every navigation and show its skeleton for a server round trip. The app layout
  (`app/(app)/layout.tsx`) now renders `AccountArea` once, at the top right of `#main`, aligned with the
  page header's first row. Layouts stay mounted across navigations, so moving between app pages never
  shows the skeleton; on a full load the menu streams in the same response (local ECC verification, so
  a few milliseconds). `PageHeader` no longer renders it and reserves room on its right (`pr-24`, enough
  for the signed-out "Sign in" link). In the DOM the menu comes before the page content, so it is the
  first stop after the skip link.
- **Rule:** components and pages read the user only through `getCurrentClaims()`, never
  `supabase.auth.getClaims()` directly (`code-standards.md`).
- **Checks:** lint, typecheck, unit tests, build and Playwright (the "Sign in" link and app-shell tests
  cover the moved menu signed out). The owner confirms on the dev server, signed in, that `/dashboard`,
  another app page and `/reset-password` show no error overlay, and that moving between app pages keeps
  the avatar in place.

**C. Sign-up check-email wording (check 10.2.2).** A repeat sign-up with a confirmed email gets no email
(Supabase's design), so "We sent a confirmation link" was untrue then. The sign-up message becomes "Check
your inbox for a confirmation link, and open it in this browser. If you already have an account, sign in
instead." It is true in both cases and still reveals nothing. Not chosen: detecting the existing account
(Supabase's `identities: []`), which would reveal whether an email has an account and relies on
undocumented behaviour.
