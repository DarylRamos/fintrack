# 1.1b Reset Link Works Again in the Same Browser

**Phase:** 1, Auth and profiles
**Status:** In progress. Approved 2026-11-17 with the default answers (A: yes, B: no). Code, tests, docs
and the development hand checks are done (2026-11-17), including the URL fix. Committed with unit 1.1a to
`development` (owner's choice: one combined commit). CI and the production check remain.
**Depends on:** Unit 1.1a (code and development hand checks done). Built before unit 1.2, and released
with units 1.1a to 1.3 in the combined pull request into `main`.

## Goal

Today a password reset link works only once. Supabase uses up the link on its first click, so a second
click shows "That link didn't work" even when the password hasn't been changed yet (owner's question on
check 10.2.6, 2026-11-17).

After this unit, clicking the reset link again **in the browser that requested the reset** opens "Set a
new password", until whichever comes first:

- 1 hour has passed since the reset was requested (the same as the link's own expiry);
- the password is changed;
- the browser signs out.

In any other case, a used link still shows the auth error page, as now.

## Why the App Has to Remember It

Supabase can't make a link work twice; email links are single-use by design (OWASP's rule for reset
links), and there is no setting for it. After the first click the browser just has a normal session.
That session looks the same before and after the password is changed, so the app can't tell "clicked
but not finished" from "finished" without keeping its own note.

A small cookie is enough for that note, because the feature is same-browser only anyway. No database
table, migration or RLS is needed.

## How It Works

1. **Requesting a reset** (`requestPasswordReset`): whenever the action ends on the check-email page, it
   also sets a `reset-pending` cookie with a 1-hour lifetime.
   - It's set on **every** path that reaches the check-email page, including the one where Supabase
     quietly refuses an unknown email. If the cookie were only set for real accounts, the response
     would reveal whether the email has an account.
   - It isn't set when the action returns an error (invalid input, rate limit, outage).
2. **Opening the link** (`/auth/confirm`):
   - A link that still works behaves exactly as now: the code is exchanged, and the browser goes to
     `/reset-password`. The cookie stays.
   - A link that doesn't work (Supabase's redirect for a used or expired link, or a failed code
     exchange) normally goes to `/auth-error`. It goes to `/reset-password` instead only when **all**
     of these hold:
     - `next` is `/reset-password` (after `safeNextPath`);
     - the request has the `reset-pending` cookie;
     - the browser is signed in (`getCurrentClaims()` returns a user).
   - Sign-up confirmation links (`next=/dashboard`) and token-hash links are unchanged.
3. **Changing the password** (`updatePassword`): on success, the cookie is deleted before the redirect
   to the dashboard. On failure, it stays, so the user can try again.
4. **Signing out** (`signOut`): deletes the cookie too. A signed-out browser would get the error page
   anyway, but this stops an old cookie from applying to whoever signs in next on that browser.

### Why this is safe

- The cookie is a hint, not a permission. It only picks the page for a browser that **already has a
  session**, and a signed-in user can already open `/reset-password` directly. It grants no access
  and holds no secret (its value is `1`).
- Links still can't be used in another browser or device, or after signing out.
- The cookie is `HttpOnly`, `SameSite=Lax` (sent when the link is opened from an email app, since that
  is a top-level navigation), `Secure` on HTTPS, and `Path=/`.
- **Shared browser:** if someone else signs in on that browser within the hour, before the cookie is
  cleared, a re-click takes them to "Set a new password" for **their own** account. That changes only
  their own password, which they can already do. Clearing on sign-out makes this unlikely, and it is
  acceptable for a single-owner app.

## Scope

**In scope**

- `lib/auth/reset-pending.ts` (new): the cookie's name, lifetime and options, with
  `markResetPending()`, `clearResetPending()` and `hasResetPending(request)`.
- `app/(auth)/actions.ts`: set the cookie in `requestPasswordReset`; clear it in `updatePassword` (on
  success) and `signOut`.
- `app/auth/confirm/route.ts`: the fallback described above.
- Unit tests (see step 4).
- Docs: this spec, `architecture.md`, `code-standards.md` (if a rule is added), `progress-tracker.md`, and
  a pointer in the 1.1a spec's Notes.

**Out of scope**

- Making a link work in another browser or device. That needs token-hash links, which need custom SMTP
  (1.1a Amendment).
- Any change to the check-email or auth-error wording (see Question B).
- Sign-up confirmation links. A re-clicked confirmation link already has an easy fix: sign in.
- A database record of reset requests.
- 2FA (`aal2`) rules for the reset flow. They come with unit 1.4.

## Questions for the Owner

Each has a recommended default. Approving the spec as written accepts the defaults.

- **A. Clear the cookie on sign-out?** Recommended: **yes** (step 3 in How It Works). The alternative
  leaves it until it expires or the password changes.

  "It keeps working in this browser for an hour, or until you set a new password."

### 2. `lib/auth/reset-pending.ts`

- `server-only`. One cookie name (for example `fintrack-reset-pending`), `RESET_PENDING_MAX_AGE = 3600`
  seconds, with a comment saying it matches Supabase's Email OTP Expiration.
- `markResetPending()` and `clearResetPending()` use `cookies()` from `next/headers`, with the options in
  How It Works. `Secure` is set when the request is HTTPS (or in production), so the cookie still works
  on `http://localhost:3000`.
- `hasResetPending(request: NextRequest)` returns whether the cookie is present with value `1`.

### 3. Actions and confirm route

- `requestPasswordReset`: call `markResetPending()` right before `redirect("/check-email?reason=reset")`,
  which covers both the success path and the quiet-refusal path, and none of the error returns.
- `updatePassword`: call `clearResetPending()` after `updateUser` succeeds, before the redirect.
- `signOut`: call `clearResetPending()` before the redirect, whether or not Supabase's call failed.
- `app/auth/confirm/route.ts`: replace each `redirectTo(request, "/auth-error")` for a link that didn't
  work (the no-code branch and the failed exchange) with one helper:
  - if `safeNextPath(next)` is `/reset-password`, `hasResetPending(request)` is true and
    `getCurrentClaims()` returns a user, redirect to `/reset-password`;
  - otherwise redirect to `/auth-error`, as now.
  - The token-hash branch and its invalid-type check stay as they are. The failed exchange is still
    logged with `logAuthError`. The fallback logs nothing new and never logs the cookie.
  - Every response keeps `Cache-Control: no-store`.
- Update the comments at the top of the route and in the actions to point to this spec.

## Decisions

- **A cookie, not a database table:** the feature is same-browser only, so the browser can hold the
  note. No schema change, migration or RLS.
- **The cookie is set whether or not the account exists:** setting it only for real accounts would
  reveal which emails have one.
- **The session is still required:** without it a re-click could open the reset page with nobody signed
  in. The cookie alone never grants anything.
- **The link stays single-use at Supabase:** only the app's response to a used link changes.
- **A separate small unit, not a 1.1a amendment:** 1.1a's checks have all passed, so this gets its own
  spec, tests, hand checks and commit, and ships in the same combined release.

## Rules to Follow

- Follow `architecture.md` and `code-standards.md`, especially the Auth rules: no account enumeration,

- Don't log or print the cookie, tokens, codes or email addresses.

## Hand-Check Fix: Supabase's Error Left in the URL (approved 2026-11-17)

**Owner's report (check 5.1):** the second click opened "Set a new password", but the address bar read
`/reset-password#error=access_denied&error_code=otp_expired&error_description=Email+link+is+invalid+or+has+expired&sb=`,
which contradicts the page.

**Cause:** Supabase reports a used link in the URL fragment (after `#`), which browsers never send to the
server. When a redirect's target has no fragment, the browser keeps the old one, so it survives
`/auth/confirm`'s redirect to `/reset-password` (and to `/auth-error`, where it went unnoticed). Cosmetic
only: it holds no token and nothing reads it.

**Fix (owner chose option A):** `components/auth/clear-auth-error-hash.tsx`, a client component rendered
once in `app/(auth)/layout.tsx`, removes the fragment with `history.replaceState` when it looks like
Supabase's error (`error=` or `error_code=`). No reload; other fragments are left alone. Option B, an
empty `#` on the server redirect, was turned down because it can leave a trailing `#`.

**Tests:** Playwright checks that the fragment is removed after `/auth/confirm`'s redirect and on
`/reset-password` and `/auth-error` directly, and that other fragments stay. Lint, typecheck, 175 unit
tests and the build pass; Playwright 56 passed, 14 skipped.

**Hand checks after the fix:** repeat check 5.1 (the URL should be plain `/reset-password`), and check
that check 5.2's error page has a plain `/auth-error` URL.
