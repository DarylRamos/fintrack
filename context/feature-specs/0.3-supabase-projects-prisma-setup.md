# 0.3 Supabase Projects, Prisma Setup and Connection Strings

**Phase:** 0, Foundation
**Status:** Complete
**Depends on:** Unit 0.2 (shadcn/ui setup and app shell). No code from it is used, but units go in order.

## Goal

Connect FinTrack to its database. When this unit is done, a development and a production Supabase project
exist, Prisma is installed and configured, and the app can run a query against the development database
through one shared, server-only Prisma Client in `lib/db`. Both projects are confirmed reachable, and the
free-plan questions that belong to this unit are answered.

## Scope

**In scope**

- Two free Supabase projects, development and production, created by the owner (see Manual Tasks)
- A dedicated `prisma` database role in each project, following Supabase's Prisma guide
- Prisma 7 installed, with `prisma.config.ts`, an empty `prisma/schema.prisma` and the generated client
- The shared Prisma Client in `lib/db/client.ts`, using the `pg` driver adapter
- Connection strings in `.env.local` (development only), and a committed `.env.example` with no secrets
- A temporary check that the runtime and migration connections both work, removed afterward
- Answering the free-plan questions this unit can answer (two active projects, pausing)
- Doc updates in `architecture.md`, `code-standards.md` and `progress-tracker.md`

**Out of scope**

- Any model, table or migration, and RLS (unit 0.4)
- Confirming whether the Prisma role bypasses RLS in practice (unit 0.4, which has tables to test on)
- Supabase Auth, its URL and keys, and the `@supabase/*` packages (Phase 1)
- Supabase Storage and the receipts bucket (Phase 2)
- Vitest, Playwright and CI (unit 0.5)
- Vercel, its environment variables and production deployment (unit 0.6)
- Backups, `pg_dump` and the pause behavior of a project with a daily job (unit 0.7)
- Seed data and `tsx`
- Prisma 8, which is still a release candidate (see Decisions)

## Manual Tasks for the Owner

These need the owner's Supabase account or secrets, so they are not done by the agent. Steps 1 to 4 must
be finished before implementation starts. Do them once for **each** project.

1. **Create the projects.** In the Supabase dashboard, create two free projects in the same region:
   - `fintrack-dev`
   - `fintrack-prod`

   Pick the region closest to you. Unit 0.6 sets Vercel's function region to match it. Save each
   project's database password in a password manager.
2. **Create the `prisma` role.** In each project's SQL Editor, run the SQL below, with a new strong
   password for each project (letters and digits only, so it needs no URL encoding). Save both passwords.

   ```sql
   create user "prisma" with password 'REPLACE_WITH_STRONG_PASSWORD' bypassrls createdb;
   grant "prisma" to "postgres";
   grant usage on schema public to prisma;
   grant create on schema public to prisma;
   grant all on all tables in schema public to prisma;
   grant all on all routines in schema public to prisma;
   grant all on all sequences in schema public to prisma;
   alter default privileges for role postgres in schema public grant all on tables to prisma;
   alter default privileges for role postgres in schema public grant all on routines to prisma;
   alter default privileges for role postgres in schema public grant all on sequences to prisma;
   ```

   This matches Supabase's Prisma guide as of 2026-11-13. Check the guide again before running it.
3. **Copy the connection strings.** In each project, open **Connect**, and copy:
   - the **Transaction pooler** string (port `6543`), for `DATABASE_URL`
   - the **Session pooler** string (port `5432`), for `DIRECT_URL`

   In both, change the user from `postgres.<project-ref>` to `prisma.<project-ref>`, and use the `prisma`
   password. Append `?pgbouncer=true` to the transaction pooler string.
4. **Fill in `.env.local`.** Agents don't edit `.env*` files, so add these two lines yourself, with the
   **development** project's strings only:

   ```bash
   DATABASE_URL="postgresql://prisma.<dev-ref>:<password>@<pooler-host>:6543/postgres?pgbouncer=true"
   DIRECT_URL="postgresql://prisma.<dev-ref>:<password>@<pooler-host>:5432/postgres"
   ```

   Keep the **production** strings in your password manager only. They go into Vercel in unit 0.6, and
   never into a file in this folder.
5. **Check production yourself** (during step 7 of Implementation). Run one command with the production
   session string typed into the terminal, so the secret never passes through the agent.

## Implementation

Do not start until the owner confirms Manual Tasks 1 to 4 are done.

### 1. Install the packages

1. Check the current Prisma docs for Prisma 7 with PostgreSQL and driver adapters, since examples online
   may target Prisma 6 or the Prisma 8 release candidate.
2. Install, pinned to exact versions:

   ```bash
   npm install --save-exact @prisma/client@7.10.1 @prisma/adapter-pg@7.10.1 pg
   npm install --save-exact --save-dev prisma@7.10.1 @types/pg @next/env@16.4.5
   ```

   - **`prisma`, `@prisma/client` and `@prisma/adapter-pg`** must share the same version. Use 7.10.1, or
     the newest stable 7.x on the day, never an `8.0.0-rc`. Do not install `prisma@latest`: on
     2026-11-13 its `latest` tag points at `8.0.0-rc.33`.
   - **`pg`** is the Postgres driver used by the adapter.
   - **`@next/env`** loads `.env.local` for the Prisma CLI the same way Next.js does. It's pinned to the
     installed `next` version, and Vitest reuses it in unit 0.5.
   - **No `server-only` package:** Next.js 16 handles `import "server-only"` itself and ships its
     types (`node_modules/next/types/global.d.ts`), and its docs say installing it is optional.
   - **No `dotenv` or `tsx`:** `@next/env` covers env loading, and there are no seed scripts yet.
3. Record the installed versions in this spec's Notes.

### 2. Prisma config and schema

Create `prisma.config.ts` at the project root:

- Load env files with `loadEnvConfig(process.cwd())` from `@next/env`, so the CLI reads `.env.local`.
- Use `defineConfig` from `prisma/config`, with `schema: "prisma/schema.prisma"` and
  `migrations: { path: "prisma/migrations" }`.
- Set the datasource URL to `DIRECT_URL`, the session pooler. Prisma Migrate needs a session connection,
  and the transaction pooler can't run migrations.
- `prisma generate` must still work when `DIRECT_URL` is unset, as on CI in unit 0.5. If Prisma's
  `env()` helper throws when a variable is missing, read `process.env.DIRECT_URL` instead. Test this
  by running `prisma generate` with the variable unset.

Create `prisma/schema.prisma` with no models:

```prisma
generator client {
  provider = "prisma-client"
  output   = "../lib/db/generated/prisma"
}

datasource db {
  provider = "postgresql"
}
```

The datasource has no `url`, because Prisma 7 reads it from `prisma.config.ts`. Check the Prisma 7 docs
before relying on this.

### 3. Generate the client

1. Add `"postinstall": "prisma generate"` to `package.json` scripts, so the client is generated after
   every `npm install`, including on Vercel. Prisma 7 no longer generates it automatically.
2. Run `npx prisma generate`. It may warn that the schema has no models, which is expected.
3. Add `/lib/db/generated/` to `.gitignore`, and `"lib/db/generated/**"` to `globalIgnores` in
   `eslint.config.mjs`.

### 4. The shared Prisma Client

Create `lib/db/client.ts`:

- Start with `import "server-only";`.
- Import `PrismaClient` from `./generated/prisma/client`, and `PrismaPg` from `@prisma/adapter-pg`.
- Create the client with `new PrismaClient({ adapter: new PrismaPg({ connectionString }) })`, where the
  connection string is `DATABASE_URL`, the transaction pooler.
- If `DATABASE_URL` is missing, throw an error that names the variable, but never print its value.
- Keep one instance on `globalThis` outside production, so hot reload in `next dev` doesn't open a new
  pool on every change.
- Export it as `db`. Nothing else in this unit imports it, except the temporary check in step 7.

Architecture invariant 3 applies from now on: only files in `lib/db/` may import from `lib/db/client.ts`
or `lib/db/generated/`. Unit 0.4 adds the first data-layer functions.

### 5. `.env.example`

1. In `.gitignore`, add `!.env.example` below the existing `.env*` line, so this one file can be
   committed.
2. Create `.env.example` with both variable names, a comment saying which pooler and port each uses, and
   placeholder URLs in the shape of Manual Tasks step 4. It must contain no real project ref, host or
   password.

### 6. Check Next.js compatibility

1. Check `node_modules/next/dist/docs/` for `serverExternalPackages` and whether `pg` and the Prisma
   packages are on its built-in list.
2. If `npm run build` fails because of how Turbopack bundles Prisma or `pg`, stop and report. Do not
   change `next.config.ts` without the owner's approval.

### 7. Confirm the connections, then remove the check

1. **Migration connection (dev):** run `npx prisma migrate status`. It must connect and report that no
   migrations exist. This proves `DIRECT_URL`, the `prisma` role and the config file work.
2. **Runtime connection (dev):** create the temporary `app/api/db-check/route.ts`. It runs
   `` db.$queryRaw`select current_user, version()` `` and returns `{ data: { user } }`, or
   `{ error: { code, message } }` with a 500 and no driver details. Open it with `npm run dev`. The user
   must be `prisma`, which proves the transaction pooler string and the role.
3. **Production:** the owner runs this in their own terminal, with the production session string:

   ```powershell
   $env:DIRECT_URL = "<production session pooler string>"; npx prisma migrate status; Remove-Item Env:DIRECT_URL
   ```

   It must connect and report no migrations. `@next/env` never overrides a variable already set in the
   shell, so this uses the production value even though `.env.local` holds the development one. The
   output names the host and database it checked; confirm it's the production project.
4. **Delete `app/api/db-check/`**, then run `npm run build` and confirm it isn't in the route list.

## Decisions

- **Prisma 7.10.1, not Prisma 8:** Prisma 8 is still a release candidate. The `prisma` CLI's npm `latest`
  tag points at `8.0.0-rc.33`, while `@prisma/client` and `@prisma/adapter-pg` are at 7.10.1. A release
  candidate doesn't suit a project holding real financial data. Upgrade to Prisma 8 in its own unit once
  it's stable.
- **A dedicated `prisma` role:** as Supabase's guide recommends. It has its own password, so it can be
  rotated without touching the dashboard's `postgres` password, and `BYPASSRLS` makes the RLS model in
  `architecture.md` explicit rather than relying on table ownership.
- **Transaction pooler at runtime, session pooler for migrations:** Vercel functions are serverless, so
  they need the transaction pooler. The direct connection is IPv6-only on the free plan and may not work
  from a home network, so migrations use the session pooler, which also supports IPv4.
- **`.env.local` for development only:** keeping production strings out of the project folder means no
  local command can reach production by accident. Production migrations take the URL from the shell for
  one command, and unit 0.4 or 0.6 documents that routine.
- **`@next/env` instead of `dotenv`:** it reads the same files with the same precedence as Next.js, and
  unit 0.5 needs it for Vitest anyway.
- **Generated client inside `lib/db/`:** keeps invariant 3 easy to check, since every Prisma import lives
  under one folder.

## Implementation Notes (2026-11-13)

- **Installed versions:** `prisma` 7.10.1, `@prisma/client` 7.10.1, `@prisma/adapter-pg` 7.10.1, `pg`
  8.23.1, `@types/pg` 8.23.1 and `@next/env` 16.4.5, all pinned exactly. 7.10.1 was still the newest
  stable 7.x on the day.
- **`env()` throws:** Prisma's `env()` helper throws `PrismaConfigEnvError` when a variable is unset, so
  `prisma.config.ts` reads `process.env.DIRECT_URL` instead. `prisma generate` was tested with the
  variable unset by running it with `NODE_ENV=test`, which makes `@next/env` skip `.env.local`.
- **`loadEnvConfig(process.cwd(), true)`:** the `true` (development mode) makes the CLI read the same
  files as `next dev`: `.env.development.local`, `.env.local`, `.env.development` and `.env`. Its source
  confirms it never overrides a variable already set in the shell.
- **npm allow-scripts:** npm 11.17 skipped the install scripts of `prisma` and `@prisma/engines`. The CLI
  and the bundled schema engine work without them, so they weren't approved, and `package.json` has no
  allow-scripts entry. The project's own `postinstall` still runs `prisma generate` on `npm install`.
- **Development project region:** `ap-southeast-2` (Sydney), seen in `migrate status` output.
- **Temporary route:** it called `await connection()` before querying, so it wasn't prerendered under
  `cacheComponents`. It returned `{"data":{"user":"prisma"}}` from `next dev`. An extra production build
  with the route present compiled Prisma and `pg` with no `next.config.ts` change, and showed the route as
  dynamic. The route was then deleted, and the final build lists only the nine app pages and `/`, all
  static.
- **Next.js external packages:** `@prisma/client`, `prisma` and `pg` are on Next's built-in
  `serverExternalPackages` list. `@prisma/adapter-pg` isn't, but it bundled without problems.
- **Production check (owner, 2026-11-13):** `migrate status` connected to `aws-0-ap-southeast-2` on port
  5432 and reported no migrations. Both projects are therefore active at the same time, in the same
  region.
- **Correction to step 7.3:** the output can't tell the projects apart, because both use the same regional
  pooler host and the project ref appears only in the username. The result relies on the owner having
  pasted the production string (user `prisma.<prod-ref>`). Later production commands need the same
  check.
