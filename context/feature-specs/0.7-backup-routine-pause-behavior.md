# 0.7 Documented `pg_dump` Routine; Backup and Project-Pause Behavior

**Status:** Complete (2026-11-16). The pause check on or after 2026-11-23 is tracked in
`progress-tracker.md`.

## Goal

Make sure FinTrack's production data can be recovered, and that production doesn't pause by surprise:

1. Confirm what Supabase's free plan does and doesn't back up, and record it.
2. Write a manual backup routine that the owner can run from Git Bash without Docker. The backups are
   encrypted, stored outside the project folder, and checked after every run.
3. Run the routine once on production and confirm the backup can be read.
4. Record what Supabase says about pausing free projects, and set a dated check that the daily
   `heartbeat` keeps production active.

This is the last Phase 0 unit. It is mostly documentation and one owner-run backup. The only repository
change outside `context/` is a `.gitignore` guard.

## Why Now

Phase 1 adds the first real data: users, sign-in identities and 2FA factors. The routine needs to exist
and be proven before that data does, not after the first thing goes wrong.

- A full restore into a fresh database (see the owner's answer C)
- Restoring the `prisma` role. Unit 0.3's steps re-create it, and the dump leaves out owners and grants.
- Changing the heartbeat. That only happens if the pause check fails.

## What Supabase Says (Checked 2026-11-15)

**Backups** (Supabase docs, "Database Backups"):

- "We automatically back up all Pro, Team, and Enterprise Plan projects on a daily basis." The free plan
  isn't on that list. Supabase tells free projects to "regularly export their data" with `db dump` and
  to keep off-site backups. The architecture's assumption of "no automatic backups" therefore holds.
  The production dashboard confirms it: the Free Plan does not include project backups.
- "Database backups do not include objects you store via the Storage API." This matters for receipts in
  Phase 2.

**Supabase's own dump tool:** `supabase db dump` "runs pg_dump in a container", and Supabase's backup
guide lists Docker Desktop as a requirement. By default it also leaves out the `auth` and `storage`
schemas. This project avoids Docker (unit 0.3), so the routine calls `pg_dump` directly.

**Tools already on the owner's machine** (checked 2026-11-15):

- `pg_dump`, `pg_restore` and `psql` 17.6, in `C:\Users\ramos\pgsql\bin` and on `PATH`.
- `gpg`, which comes with Git Bash.
- No Docker and no Supabase CLI.

`pg_dump` can dump servers of its own major version or older. The development project runs 17.11
(unit 0.5) and so does production (owner, 2026-11-15), so a 17.x client works.

**Pausing** (Supabase docs, "Free Plan Pausing"):

- A free project pauses if it "does not receive sufficient user database activity over the past week".
- "Typically a few user requests to the database each day over the previous week is enough to keep the
  project from being paused."
- The docs don't say whether a scheduled `SELECT 1` counts as user activity. Step 7 checks it in
  practice.
- "You can restore a paused project for up to 1 year after it was paused." That is longer than the
  earlier notes assumed.

## What a Backup Contains

Each backup is two encrypted files, both made with the `postgres` role over the session pooler.

1. **`public` schema, structure and data** (`fintrack-backup-prod-<date-time>-public.dump.gpg`)
   - `pg_dump` in custom format, so single tables can be restored later.
   - Holds every application table, `_prisma_migrations`, and the RLS settings.
   - `--no-owner --no-privileges`: a restore makes whoever runs it the owner (the `prisma` role) and
     adds no grants. That matches how unit 0.4 set things up.
2. **`auth` schema, data only** (`fintrack-backup-prod-<date-time>-auth.sql.gpg`)
   - Users, identities and 2FA factors. Supabase owns the `auth` tables, so only their rows are backed
     up; a new project already has the tables.
   - Without this file, a restored database would have data owned by user IDs that no longer exist.
     `profiles.id` holds the auth user's ID.
   - It is empty until Phase 1 but still worth taking now: the first run proves the `postgres` role can
     read it.

**Why the `postgres` role, not `prisma`:** `prisma` can read `public` but isn't meant to touch `auth`.
The `postgres` password is already in the owner's password manager from unit 0.3. The dump is
read-only, and nothing is ever restored into production with this routine.

**Why encryption:** the `auth` file will hold password hashes and 2FA secrets. `pg_dump` pipes straight
into `gpg --symmetric` with AES-256, so no unencrypted copy is ever written to disk. The passphrase
lives in the password manager.

## Owner's Answers (2026-11-15)

**A. Cadence (confirmed 2026-11-16):** monthly, plus a backup before every production migration. The
owner chose this lighter option over weekly backups.
- **Monthly:** on the first day of each month, from 2026-12-01. Each backup is a full copy of the
  database at that moment, so the worst case is losing up to a month of entries, which would be re-entered
  from statements.
- **Before every production migration:** just before `migrate deploy`. This becomes step 0 of the
  Production Migrations routine in `architecture.md`.
- **First backup:** taken in this unit, to prove the routine.
- **Retention:** keep the last 12 monthly backups. Delete each pre-migration backup once the next
  monthly backup has passed its checks.
- **File names** include the time (`<YYYY-MM-DD-HHMM>`), so a pre-migration backup on the 1st doesn't
  overwrite the monthly one.

**B. Location:** `C:\Users\ramos\Documents\FinTrack-backups` on this machine, outside the project folder.
No second copy for now. Losing or wiping the laptop would lose the backups, so revisit this in Phase 2,
when real data starts.

**C. Restore test:** as recommended. This unit proves each backup is complete without restoring it:
decrypt it, list its contents with `pg_restore --list`, and compare the `_prisma_migrations` rows with
`prisma migrate status`. A full restore drill comes in Phase 2, once the first real tables exist, into
the development project or a throwaway local server, with its own approval. Reason: a real restore needs
an empty Postgres 17 server; the owner's `pgsql` folder has client tools only, CI can't hold backups,
and restoring into development would overwrite its `public` schema.

**D. Pause check:** as recommended. Unit 0.7 is complete once the backup checks pass. The pause check
(on or after 2026-11-23, after 7 or more daily heartbeats from 2026-11-16) is tracked as a dated
follow-up in `progress-tracker.md`, so the combined 0.6 + 0.7 commit isn't held for a week.

## Decisions

- **Plain `pg_dump`, not `supabase db dump`:** no Docker, which unit 0.3 avoided on purpose. The
  client is already installed. `supabase db dump` would also skip `auth` by default.
- **`postgres` role over the session pooler:** it can read `auth`, and the direct connection is
  IPv6-only on the free plan (unit 0.3).
- **Custom format for `public`, plain SQL for `auth` data:** custom format allows restoring single
  tables. `auth` rows are restored into a Supabase project that already has the tables.
- **Encrypted in the pipe with `gpg`:** no new tool, and no unencrypted copy on disk.
- **Backups never touch GitHub or CI:** the repository is public, and CI has no secrets.

## Rules

- The agent never handles production connection strings, the `postgres` password or the backup
  passphrase. It never runs `pg_dump`, `pg_restore` or `psql` against production. The owner runs every
  production step.
- The agent's rehearsal uses only the development database, a throwaway passphrase and the scratchpad.
  It deletes its files afterwards.
- No restore into either Supabase project in this unit.
- No changes to `.env*` files, grants, roles or Supabase settings.
- Commit only with the owner's approval. The owner wants units 0.6 and 0.7 committed together.
