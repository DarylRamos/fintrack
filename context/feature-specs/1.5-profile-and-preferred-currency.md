unit:

- `/profile` shows the user's **sign-in email** (read-only), a **display name** and a **preferred
  currency**, saved with one **Save** button.
- The name appears in the account menu ("Signed in as" becomes the name above the email), and the avatar
  shows the name's first letter instead of the email's.

  4). Nothing converts amounts yet; there are no amounts.
- FinTrack gets its **first application table**, `profiles`, with RLS on, the data layer's first
  user-owned queries, and the first **cross-user access test** (success criterion 9).
- The Phase 1 open question on **schema naming conventions** is settled (Question D), so every later table
  follows the same rules.

them to Phase 6, where alerts exist (Question A).

## Data Model

### The `profiles` table

One row per user, keyed by the Supabase auth user's ID (as `architecture.md` → Storage Model already says:
no database foreign key to `auth.users`, because Prisma must not model the `auth` schema).

```prisma
model Profile {
  /// The Supabase auth user's ID (the token's `sub`). No foreign key: Prisma doesn't model `auth`.
  id                String   @id @db.Uuid
  displayName       String?  @map("display_name") @db.VarChar(50)
  preferredCurrency String   @map("preferred_currency") @db.Char(3)
  createdAt         DateTime @default(now()) @map("created_at") @db.Timestamptz(3)
  updatedAt         DateTime @updatedAt @map("updated_at") @db.Timestamptz(3)

  @@map("profiles")
}
```

- **Owner column:** invariant 3 asks every user-owned row for a `user_id`. For `profiles` the primary key
  *is* the user ID, so `id` plays that role; every query filters on `id = userId`. Every other table keeps a
  separate `user_id` column. `architecture.md` records this one exception.
- **No database default for the currency:** the default lives in one place, `DEFAULT_CURRENCY` in
  `lib/money/currencies.ts`, and the data layer passes it when it creates the row.
- **Migration** (`npx prisma migrate dev --create-only --name profiles`, then hand-added SQL, per
  `code-standards.md`):
  - `ALTER TABLE "profiles" ENABLE ROW LEVEL SECURITY;` (invariant 4; no policies).
  - `ALTER TABLE "profiles" ADD CONSTRAINT "profiles_preferred_currency_format" CHECK
    ("preferred_currency" ~ '^[A-Z]{3}$');` A format guard only; which codes are allowed is the app's
    list, which may grow without a migration.
  - `ALTER TABLE "profiles" ADD CONSTRAINT "profiles_display_name_not_blank" CHECK ("display_name" IS NULL
    OR length(btrim("display_name")) > 0);` An empty name is stored as `NULL`.

### When the row is created

**Lazily, on the first save.** Reading a user with no row returns the defaults (no name, `DEFAULT_CURRENCY`)
without writing anything. Saving is an `upsert` on `id`. This works for every way an account comes to exist
(email sign-up, Google, or a user added in the Supabase dashboard, as the test account was) with no
database trigger on Supabase's `auth.users`, no hand-written function in the `auth` schema, and no change to
the sign-up actions.

### Schema conventions (Question D, recorded in `code-standards.md` → Prisma)

| Item | Convention | Example |
| --- | --- | --- |
| Model names | PascalCase, singular | `Profile`, `Transaction`, `GoalMilestone` |
| Table names | snake_case, plural, through `@@map` | `profiles`, `goal_milestones` |
| Field names | camelCase in Prisma, snake_case columns through `@map` | `preferredCurrency` → `preferred_currency` |
| Primary keys | `id`, a UUID: `@id @default(dbgenerated("gen_random_uuid()")) @db.Uuid` (Postgres makes it, so raw SQL inserts and Prisma agree). `profiles.id` is the exception: the auth user's ID, no default. | |
| Owner column | `userId String @map("user_id") @db.Uuid`, indexed, on every user-owned table | |
| Timestamps | `createdAt` (`@default(now())`) and `updatedAt` (`@updatedAt`), both `@db.Timestamptz(3)` | |
| Calendar dates | `@db.Date` (a transaction's date, per `code-standards.md`) | |
| Money and rates | As `code-standards.md` already says: `@db.Decimal(19, 4)`, `@db.Decimal(28, 10)` | |
| Currency codes | `@db.Char(3)`, ISO 4217, upper case | |
| Constraint names | `<table>_<column>_<rule>` for hand-added checks | `profiles_preferred_currency_format` |

## Currencies

- **`lib/money/currencies.ts`** (new; Phase 2's money module grows around it, no database code):
  - `SUPPORTED_CURRENCIES`: the ISO 4217 codes Frankfurter publishes (the provider Phase 3 uses), as a
    fixed `as const` list. Expected, to be confirmed in step 1 against Frankfurter's currency list:
    AUD, BGN, BRL, CAD, CHF, CNY, CZK, DKK, EUR, GBP, HKD, HUF, IDR, ILS, INR, ISK, JPY, KRW, MXN, MYR, NOK,
    NZD, PHP, PLN, RON, SEK, SGD, THB, TRY, USD, ZAR.
  - `type CurrencyCode`, `isSupportedCurrency(code)`, `DEFAULT_CURRENCY` (Question C).
  - `currencyName(code)`: the English name from `Intl.DisplayNames` (such as "Singapore Dollar"), so no
    names are typed by hand.
- **The app never calls Frankfurter in this unit.** Step 1's check is a one-off look at its public
  currency list by the agent; the provider interface and adapter stay in Phase 3 (`ai-workflow-rules.md`:
  a new provider and the features that use it are split).
- A currency outside the list (Phase 2's open question) would need manual rates or another provider, so
  it isn't offered. Question C asks the owner to confirm their currencies are in the list.

## Data Layer

`lib/db/profiles.ts` (new, `server-only`; the only file that touches the `profiles` table):

```ts
export interface ProfileView {
  displayName: string | null;
  preferredCurrency: CurrencyCode;
}

export async function getProfile(userId: string): Promise<ProfileView>;
export async function saveProfile(userId: string, input: ProfileView): Promise<ProfileView>;
```

- `userId` is required and always comes from the verified session, never from input (invariant 3).
- `getProfile` reads `where: { id: userId }`; no row → the defaults. A stored code no longer in
  `SUPPORTED_CURRENCIES` (only possible if the list shrinks) also reads as the default, so the page never
  shows a value the form can't save.
- `saveProfile` is an `upsert` on `{ id: userId }` and returns what was saved, as plain strings.
- Not cached (invariant 9).

## Server Action

`updateProfile(input)` in `app/(app)/profile/actions.ts` (new), a public endpoint like every action:

1. `getSignedInUser()`; `null` → an error result (signed out, or 2FA still owed; invariant 6).
2. Validate with `profileSchema` (`lib/validation/profile.ts`, new, shared with the form):
   - `displayName`: trimmed; empty → `null`; otherwise 1 to 50 characters, with no control characters
     (`\p{Cc}`).
   - `preferredCurrency`: one of `SUPPORTED_CURRENCIES`.
3. `saveProfile(user.userId, values)`.
4. Ask Next.js to re-render the current page's server parts, so the account menu shows the new name at once
   (`refresh()` from `next/cache` in Next.js 16; confirmed in step 1 from the bundled docs).
5. Return `{ data: ProfileView }`, or `{ error: { code, message, fieldErrors? } }`.

| Code | When | Message |
| --- | --- | --- |
| `NOT_SIGNED_IN` | No session, or 2FA owed | "Your session has ended. Sign in again." |
| `INVALID_INPUT` | Zod failure (with `fieldErrors`) | "Check the highlighted fields." |
| `SAVE_FAILED` | The database call throws | "Couldn't save your profile. Try again." |

- These codes live in the action file. Auth's `NOT_SIGNED_IN` message is about email links, so it isn't
  reused. When Phase 2 adds the second data action, the shared shape moves to one module.
- Logging: a failed save logs only the error's `name` (and Prisma's `code`, such as `P1001`), never the
  name, currency, user ID or query.

## Where the Name Appears (Question E)

- **Account menu** (`components/app-shell/user-menu.tsx`): the label shows the display name (`font-medium`)
  above the email (muted), or only the email when no name is set. The avatar's letter is the name's first
  letter, else the email's.
- `AccountArea` reads `getProfile(user.userId)` after `requireUser()`. **If the read fails** (database
  unreachable, or the production migration missing), it logs the error's name and falls back to the email,
  so the shell never turns into an error page because of a name.
- **No "Hi, <name>" greeting yet.** `ui-context.md` plans one beside the avatar, but a variable-width
  greeting needs the header's reserved room (`pr-14`) to grow, and phones have no space for it. It arrives
  with the header's settings and notification icons (Phase 6), when that room is redesigned anyway.

  That also answers Phase 2's open question. (2) **The default for a profile that was never saved:**

  currency as the default, since you are the only user.
- **D. Schema conventions** (Phase 1 open question, deferred on 2026-11-13 to the first application table).
  **Recommended: the table in Data Model → Schema conventions** (PascalCase singular models, snake_case
  plural tables and columns, Postgres-generated UUID keys, `timestamptz(3)` timestamps). Alternatives:
  `cuid()` or Prisma-generated UUIDv7 keys (made by Prisma Client, so raw SQL inserts would need their own),

## Decisions

- **The profile row is created on first save, not by a trigger:** works for every sign-up path, and keeps
  the `auth` schema untouched.
- **The currency list is static in the app, matching Frankfurter:** no provider call before Phase 3; a code
  the rate provider can't price is never offered.
- **The header never fails because of the profile:** a failed read falls back to the email.
- **`profiles.id` is the owner column:** the one table whose key is the user ID.

## Rules to Follow

- Follow `architecture.md` and `code-standards.md`: the user ID only from the session, Zod before any
  logic, Prisma only inside `lib/db`, RLS on with no policies, no `db push`, no edits to the applied `init`
  migration.
- Never log names, currencies, user IDs, emails or connection details, including in CI's public logs and
  Playwright output.
- Never run anything against production. Don't edit `.env*` or `components/ui/*` (add shadcn components
  through the CLI).
- Don't commit until the owner says so.

### Production check query (Manual Task 2.3, read-only)

Run in the production SQL Editor after `migrate deploy`:

```sql
select c.relname as table, pg_get_userbyid(c.relowner) as owner,
       c.relrowsecurity as rls, c.relforcerowsecurity as forced,
       (select string_agg(distinct grantee, ', ') from information_schema.role_table_grants g
         where g.table_schema = 'public' and g.table_name = c.relname) as grantees,
       (select count(*) from pg_policies p
         where p.schemaname = 'public' and p.tablename = c.relname) as policies,
       (select string_agg(conname, ', ' order by conname) from pg_constraint k
         where k.conrelid = c.oid) as constraints
from pg_class c join pg_namespace n on n.oid = c.relnamespace
where n.nspname = 'public' and c.relkind in ('r', 'p')
order by 1;
```

Expected for both rows (`_prisma_migrations`, `profiles`): owner `prisma`, `rls` true, `forced` false,
grantees `prisma` only, 0 policies; `profiles` lists `profiles_display_name_not_blank`, `profiles_pkey` and
`profiles_preferred_currency_format`. If `profiles` is owned by `postgres` or has other grantees, the
migration ran with the wrong string: stop and tell the agent (the fix is the one used for
`_prisma_migrations` in unit 0.4).
