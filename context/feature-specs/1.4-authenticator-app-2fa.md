## Goal

Today a password or a Google account is enough to reach every page. After this unit:

- A signed-in user can turn on two-factor authentication (2FA) in **Settings**: scan a QR code (or type
  a setup key) into an authenticator app, then enter a 6-digit code to confirm it.
- From then on, **every** sign-in (email and password, Google, or a password reset link) stops at a
  **"Enter your code"** page before any app page opens. Success criterion 1 and invariant 6.
- Sessions that were already open on other devices when 2FA was turned on can't see app pages again
  without the code. (Supabase in fact signs them out when the new factor is verified; see Implementation
  Notes.)
- The user can turn 2FA off again in Settings, after entering a current code.
- A user who never turns 2FA on sees no change, apart from the new Settings section.

2FA stays optional, as `project-overview.md` describes ("can enable"). Authenticator apps (TOTP) only:
no SMS or phone factor (out of scope, and paid), no passkeys or WebAuthn.

## How Supabase 2FA Works

Supabase Auth includes TOTP 2FA on every plan, including Free, and it is on by default.

- **Assurance levels.** Every access token carries an `aal` claim: `aal1` after a password, Google or
  email link, and `aal2` after a correct 2FA code. Supabase upgrades the session's tokens to `aal2` when
  a code is verified; the new tokens reach the browser through the session cookies as usual.
- **Factors.** A user's factors (`verified` or `unverified`) live in Supabase's `auth` schema. They are
  **not** in the access token, so the token alone can't tell "has 2FA, hasn't entered the code yet"
  apart from "has no 2FA". Both are `aal1`.
- **The calls this unit uses** (all in `@supabase/supabase-js` 2.119.0, through the existing server
  client, so no browser Supabase client is added):
  - `mfa.enroll({ factorType: "totp", friendlyName, issuer })` → an `unverified` factor, its QR code
    (SVG), its secret and its `otpauth://` URI.
  - `mfa.challengeAndVerify({ factorId, code })` → verifies a code; the first success also marks the
    factor `verified`. Either way the session becomes `aal2`.
  - `mfa.unenroll({ factorId })` → removes a factor. Supabase requires `aal2` to remove a verified one.
  - `getUser()` → the user, including `factors`, fetched from Supabase Auth (a network call, so it can be
    trusted, unlike the user object in the cookie).
- **Why not trust the cookie's factor list:** the session cookie also holds a copy of the user with its
  factors, but the browser can edit it (the cookie isn't `HttpOnly`, by `@supabase/ssr`'s design).
  Someone with a stolen password could delete the factor list from their own cookie and skip 2FA. The
  factor check must come from Supabase itself (Question A).

## Session States

`lib/auth` gains one idea that every check shares, the **session state**:

| State | Meaning |
| --- | --- |
| `signed-out` | No session, or the token can't be verified (as today). |
| `needs-2fa` | Verified token at `aal1`, and the user has a **verified** TOTP factor. |
| `signed-in` | Verified token at `aal2`, or at `aal1` with no verified factor. |

How it is worked out (`getSessionState`, in a new `lib/auth/assurance.ts`, used by the proxy and by
`session.ts`):

1. `getClaims()` as today. No claims → `signed-out`.
2. `aal` is `aal2` → `signed-in`, with **no network call**.
3. Otherwise `getUser()`, and look for a factor with `factor_type: "totp"` and `status: "verified"`.
   Found → `needs-2fa`; none → `signed-in`.
4. If `getUser()` fails (Supabase unreachable, user deleted), the result is `needs-2fa`, never
   `signed-in` (fail closed). The 2FA page then fails too and shows the generic error; signing out still
   works.

**Cost:** step 3 is one call to Supabase Auth, made only for `aal1` sessions. Once the owner turns 2FA on,
every session is `aal2` after the code, so normal browsing makes no extra call. A user without 2FA pays one
call per page request (both projects and the functions are in Sydney). Within one render the result is
shared with React's `cache()`, so the proxy and the page make at most one call each.

## Route Rules

`routeDecision` (`lib/auth/routes.ts`) takes `state` instead of `signedIn`. The `signed-out` and
`signed-in` columns are today's rules unchanged; `needs-2fa` is new.

| Path | `signed-out` | `needs-2fa` | `signed-in` |
| --- | --- | --- | --- |
| `/` | `/sign-in` | `/two-factor` | `/dashboard` |
| Guest pages (`/sign-in`, `/sign-up`, `/forgot-password`) | shown | `/two-factor?next=<safe next>` | `safeReturnPath(next)` |
| **`/two-factor`** (new) | `/sign-in` | shown | `safeTwoFactorNext(next)` |
| `/reset-password` | shown | `/two-factor?next=/reset-password` | shown |
| `/check-email`, `/auth-error` | shown | shown | shown |
| `/auth/*`, `/api/*` | passed through | passed through | passed through |
| Every other page (protected) | `/sign-in?next=<page>` | `/two-factor?next=<page>` | shown |

- As today, only `GET` and `HEAD` are redirected, redirects are `307` through `redirectWithSession`, and
  `/api/cron/*` never reaches the proxy.
- `/two-factor` is a new kind of public page in `lib/auth/paths.ts` (`TWO_FACTOR_PATH`), so
  `safeReturnPath` refuses it as a return target.
- **`safeTwoFactorNext(next)`** (`lib/auth/redirect.ts`): `/reset-password` if `next` is exactly that,
  otherwise `safeReturnPath(next)`. It exists because a reset link signs the browser in at `aal1`; with
  2FA on, the user must enter a code before setting a new password, then continue to the reset page.
  `safeReturnPath` itself is unchanged.
- **Password reset can't bypass 2FA:** the reset link gives an `aal1` session, the proxy sends it to
  `/two-factor`, and `updatePassword` refuses a `needs-2fa` session on the server too.
- **Guest pages in `needs-2fa`** go to `/two-factor`, which has a **Sign out** button for "use a
  different account" (Question F).

## Server-Side Checks (the Authorization Boundary)

The proxy only routes. The real checks are in server code, as today:

- **`requireUser()`** (pages and Server Components) returns the user only in `signed-in`. In `needs-2fa`
  it redirects to `/two-factor`; in `signed-out`, to `/sign-in` (as today). This is the single place
  1.2a reserved for the `aal2` check.
- **`getCurrentClaims()`** keeps its meaning: any verified session, either level. It gains `aal` in its
  result. Only auth code uses it directly (the 2FA actions must work in `needs-2fa`).
- **New `getSignedInUser()`** (`session.ts`) for Server Actions that touch user data (from Phase 2): the
  user only in `signed-in`, otherwise `null`, so the action returns `NOT_SIGNED_IN`. `code-standards.md`
  is updated so data actions use it, never `getCurrentClaims()`.
- **`updatePassword`** uses `getSignedInUser()`'s state check: `needs-2fa` returns an error result, so a
  reset can't be finished without the code even by calling the action directly.
- Invariant 6 is met because every page reads the user through `requireUser()` and every data action
  through `getSignedInUser()`. Prisma isn't involved: there is no app data yet, and no data-layer change.

## Flows

### Turning 2FA on (`/settings`)

1. **Off:** the Security section shows "Two-factor authentication", "Off", one line of explanation and a
   **Set up** button.
2. **Set up** calls `startTwoFactorSetup()`. The action requires `signed-in`, refuses if a verified TOTP
   factor already exists (`TWO_FACTOR_ALREADY_ON`), removes any leftover `unverified` TOTP factors (from
   an abandoned setup, so the friendly name doesn't clash), then calls `mfa.enroll` with
   `friendlyName: "Authenticator app"` and `issuer: "FinTrack"`. It returns `{ factorId, qrCode, secret }`
   to the form. Nothing about the factor is written to the page's server render, so the secret is never
   part of a cached or prerendered payload.
3. The section shows the QR code, **"Can't scan it? Enter this setup key"** with the secret (grouped in
   fours, monospace) and a **Copy** button, then the **Code** field and **Turn on** (primary) and
   **Cancel**.
4. **Turn on** calls `confirmTwoFactorSetup({ factorId, code })`: requires `signed-in`, checks that the
   factor belongs to the user and is `unverified` (from `getUser()`), then `challengeAndVerify`. Success:
   the factor is verified, this session becomes `aal2`, and the section shows **On**. Every other session
   of this user is now `needs-2fa`.
5. **Cancel** calls `cancelTwoFactorSetup({ factorId })`, which removes the unverified factor (only if
   it is the user's and still unverified). Leaving the page without cancelling leaves an unverified
   factor behind; it does nothing, and the next **Set up** removes it.

### Signing in with 2FA on

- **Email and password:** `signIn` already receives the user from `signInWithPassword` (straight from
  Supabase, so trusted). With a verified TOTP factor it redirects to
  `/two-factor?next=<safeReturnPath(next)>`; otherwise to `safeReturnPath(next)` as today.
- **Google:** `/auth/callback` does the same with the user from `exchangeCodeForSession` (the note left in
  the 1.3 spec).
- **Email links (`/auth/confirm`):** unchanged. A sign-up confirmation is a new user with no factor. A
  reset link goes to `/reset-password`, and the proxy sends a `needs-2fa` session to
  `/two-factor?next=/reset-password`. 1.1b's re-click fallback works the same way.
- **On `/two-factor`:** one **Code** field and **Verify**. The page is static; `next` is read from the
  address bar at submit time, as `SignInForm` does. `verifyTwoFactor({ code, next })` requires a session
  (`getCurrentClaims()`), finds the user's verified TOTP factor (`getUser()`), calls
  `challengeAndVerify`, then redirects to `safeTwoFactorNext(next)`. A wrong code shows "That code didn't
  work. Check your authenticator app and try again." and keeps the user on the page.
- **Sign out** on `/two-factor` is the existing `signOut` action.

### Turning 2FA off (`/settings`)

- **On:** the section shows "On", "Added <date>" (the factor's `created_at`, with `Intl`) and a **Turn
  off** outline button.
- **Turn off** opens a small dialog: "Enter a current code to turn off two-factor authentication", the
  **Code** field, **Turn off** and **Cancel** (Question D).
- `disableTwoFactor({ code })` requires `signed-in`, verifies the code against the user's factor
  (`challengeAndVerify`), then `unenroll`s it, then refreshes the session so the tokens carry the new
  state. The section shows **Off**.

### Lost authenticator app (Question C)

No in-app recovery in this unit. The owner's recovery paths, documented in `architecture.md`:

1. **The setup key** saved in the password manager during setup (Manual Task 5): any authenticator app
   can be set up again from it.
2. **The Supabase dashboard:** Authentication → Users → the user → remove the MFA factor. The next
   sign-in then needs no code. This is why the owner's Supabase account must have its own 2FA (Manual
   Task 2).

## Errors

New codes in `lib/auth/errors.ts`:

| Code | When | Message |
| --- | --- | --- |
| `INVALID_CODE` | Supabase `mfa_verification_failed`, `mfa_challenge_expired`, or a code that isn't 6 digits (field error) | "That code didn't work. Check your authenticator app and try again." |
| `TWO_FACTOR_ALREADY_ON` | Setup started while a verified factor exists (`mfa_verified_factor_exists`, or found by the action) | "Two-factor authentication is already on." |
| `TWO_FACTOR_REQUIRED` | A `needs-2fa` session calls `updatePassword` or a 2FA settings action; Supabase `insufficient_aal` | "Enter your authentication code first." (the form also links to `/two-factor`) |

- Rate limits (`over_request_rate_limit`, HTTP 429) map to the existing `RATE_LIMITED`. Supabase limits
  code verification attempts; step 1 confirms the limit.
- Anything else maps to `AUTH_FAILED` ("Something went wrong. Try again."), logged with `logAuthError`
  (name and code only).
- **Never logged or printed:** codes, the TOTP secret, the QR code, the `otpauth://` URI, factor IDs,
  `next` values, emails.

**Validation** (`lib/validation/auth.ts`): `twoFactorCodeSchema` trims and removes spaces, then requires
exactly 6 digits; `factorId` is a UUID; `next` as in `signInActionSchema`.

## Questions for the Owner

Answered: **A to E, the recommended options** (2026-11-20); **F, the recommended option** (2026-11-23).

- **A. How does the server know a user has 2FA?** **Recommended: ask Supabase (`getUser()`) only for
  `aal1` sessions**, as in Session States. No setup, nothing new to maintain; once your 2FA is on, normal
  browsing makes no extra call. Alternative: a Supabase **Custom Access Token hook** (a Postgres function
  that adds a "has 2FA" claim to every token) makes the check free on every request, but adds a hand-written
  database function, grants to Supabase's auth role and a dashboard setting in both projects, all for a
  saving that disappears once 2FA is on.
- **B. Where does the 2FA setting live?** **Recommended: a Security section on `/settings`**, replacing
  its placeholder. Profile (unit 1.5) keeps personal details and currency; later settings (privacy,
  themes) join `/settings`. Alternative: a separate `/settings/security` page.
- **C. Recovery if the phone is lost?** **Recommended: one authenticator factor, plus the setup key saved
  in your password manager, with the Supabase dashboard as the last resort** (see Flows). Alternatives: a
  second authenticator factor as a backup (more UI: a list of factors), or wait for Supabase's recovery
  codes (experimental today).
- **D. What does turning 2FA off require?** **Recommended: a current code** (an unattended signed-in
  browser can't turn it off). Alternative: a confirm dialog only (Supabase already requires an `aal2`
  session).
- **E. Automated tests of the real 2FA flow, and Supabase's local stack in CI (the decision 1.1a and
  1.2a left for "before unit 1.4")?** **Recommended: no local stack in CI (still Docker and minutes per
  run); add a local-only Playwright test with a second development test account** that turns 2FA on,
  signs out, signs in with a code, and turns 2FA off, computing codes from the setup key shown on the page
  (a small `node:crypto` helper, no new dependency). It skips in CI and when its variables aren't set, like
  the signed-in tests. The existing test account keeps 2FA **off**, so the other signed-in tests keep
  working. Alternative: hand checks only for the real flow; unit tests still cover every branch with mocks.
- **F. A `needs-2fa` browser on `/sign-in`?** **Recommended: send it to `/two-factor`**, which offers
  **Sign out** for "use a different account". One place to finish or leave. Alternative: show the sign-in
  page (a second sign-in replaces the half-finished session).

## Decisions

- **TOTP only, optional:** as `project-overview.md` says; SMS is out of scope and paid.
- **Factors read from Supabase, never the cookie:** the cookie's user copy can be edited by the browser.
- **Fail closed:** when the factor check fails, the session is `needs-2fa`, never `signed-in`.
- **One session-state helper for the proxy and the server checks:** they can't drift apart.
- **The proxy routes; `requireUser()` and `getSignedInUser()` authorize:** as in 1.2a.
- **A reset link can't skip 2FA:** the code comes before the new password.
- **Server Actions only, no browser Supabase client:** as every other auth step.

## Rules to Follow

- Follow `architecture.md` and `code-standards.md`, especially Auth: validate input first, never
  `getSession()` on the server, no account enumeration, log only an error's `name` and `code`.
- Never log or print codes, TOTP secrets, QR codes, `otpauth://` URIs, factor IDs, tokens, cookies, `next`
  values, emails or the test accounts' credentials, including in Playwright output and screenshots kept in
  the repository.
- `proxy.ts`'s matcher is unchanged; `/api/cron/*` is never touched.
- No schema or migration change. Never run anything against production. Don't edit `.env*` or
  `components/ui/*` (add shadcn components through the CLI).
- Don't commit until the owner says so.

## Implementation Notes (2026-11-23)

- Built as specified, with the differences below. No schema, migration, Prisma, cron, `vercel.json`,
  matcher, Supabase-setting, Vercel or env change. shadcn `dialog` added with the CLI
  (`components/ui/dialog.tsx`).
- **Step 1 findings** (from the installed auth-js 2.119.0):
  - `mfa.enroll` returns `totp.qr_code` (a data URL), `secret` and `uri`; `challengeAndVerify` saves the
    `aal2` session through the cookie storage, so a Server Action's `setAll` writes it (confirmed by the
    browser test); `signInWithPassword` and `exchangeCodeForSession` return the user with `factors`;
    `getClaims()` exposes `aal`.
  - **Verifying a factor signs out the user's other sessions** (auth-js docs: "all other sessions are
    logged out"). So other browsers land on `/sign-in`, not `/two-factor`, after 2FA is turned on: their
    `aal1` token asks Supabase for the user, which answers that the session is gone. Goal and hand check
    7.5 were corrected.
  - Not confirmed from Supabase's hosted docs (no web check this session): whether `updateUser({ password
    })` itself needs `aal2`, and the exact verification rate limit. Neither changes the design:
    `updatePassword` refuses `needs-2fa` itself, and HTTP 429 maps to `RATE_LIMITED`.
- **Names:** the spec's `getSessionState` is `getSessionStatus()` (returns the state and the user);
  `assuranceState()` in `lib/auth/assurance.ts` does the factor check. `getTwoFactorStatus()` reads the
  Settings row's state. `twoFactorPath(next)` builds `/two-factor?next=…` and leaves out the default
  `/dashboard`.
- **Session gone vs Supabase unreachable:** when `getUser()` reports a missing or revoked session
  (`AuthSessionMissingError`, 401, `session_not_found`, `user_not_found`), the state is `signed-out`, not
  `needs-2fa`, so a signed-out-elsewhere browser goes to `/sign-in`. Any other error fails closed as
  `needs-2fa`, logged by name and code only.
- **QR code format:** Supabase's SVG starts with `<?xml …?>` and a `<!-- Generated by SVGo -->` comment;
  the first check refused it (found by the browser test). The check now allows both; the SVG is

  text only.
- **`useAuthForm`** accepts an action that returns nothing on success (Settings' forms don't redirect).
