## Goal

Today a missing page shows Next.js's built-in "404 | This page could not be found." screen, and an
unexpected error shows Next.js's built-in error screen. Neither looks like FinTrack or offers a way back.
After this unit:

- A missing page shows a FinTrack **"Page not found"** page with one way back home.
- An unexpected error while rendering a page shows a FinTrack **"Something went wrong"** page with
  "Try again" and a way back home. It never shows the error's message or stack.
- An error in the root layout itself shows the same page, from `app/global-error.tsx`.
- Every error page follows `ui-context.md`, works at phone width, and works in light and dark mode.

401 and 403 pages aren't planned (decided on 2026-11-17): the proxy sends signed-out visitors to
sign-in, and in Phase 2 another user's record answers 404, so its existence isn't revealed.

## When Each Page Appears

| Situation | What renders | HTTP status |
| --- | --- | --- |
| Signed in, a URL that matches no route (`/nope`) | `app/not-found.tsx` | `404` (to confirm in step 1) |
| Signed out, a URL that matches no route (`/nope`) | The proxy sends it to `/sign-in?next=%2Fnope` first (unit 1.2a). After sign-in, `/nope` shows the 404 page | `307`, then `404` |
| Either state, an unknown path under a passed-through prefix (`/auth/nope`, `/api/nope`) | `app/not-found.tsx` (the proxy doesn't redirect these) | `404` (to confirm in step 1) |
| `notFound()` called by a page (Phase 2: a record that doesn't exist or isn't the user's) | `app/not-found.tsx`, until a nearer `not-found.tsx` exists (see Question A) | `404` before streaming starts; `200` with `noindex` after |
| An error thrown while rendering a page or a nested layout | `app/error.tsx` | `500` before streaming starts; `200` after (see below) |
| An error thrown in the root layout (`app/layout.tsx`) | `app/global-error.tsx` | As above |
| A Server Action that fails | Not an error page: actions return `{ error: { code, message } }` and the form shows it (unchanged) | n/a |
| A Route Handler that fails (`/auth/confirm`, `/api/cron/*`) | Not an error page: each handler answers for itself (unchanged) | n/a |

About the status codes: Next.js fixes the status when it starts streaming. Under Cache Components most
pages send a static shell first, so an error in dynamic content after that keeps `200`. The bundled docs
say Next.js adds `<meta name="robots" content="noindex">` to streamed 404s. "500 page" in this unit means
the page the user sees, not a guaranteed status. The tests assert the `404` status only where step 1
confirms it.

## The Pages

Both pages share one layout: a calm, centred column, standalone (no sidebar, no auth brand panel), on
`--bg-base`, at full viewport height.

- The **"FinTrack"** text wordmark at the top (`font-semibold`), as on the auth pages on phones.
- A short label above the title in `text-sm font-medium text-ink-muted`.
- The title as the page's only `h1`, `text-2xl font-semibold`.
- One sentence in `text-sm text-ink-muted`.
- The actions: one primary pill button (`h-11 rounded-full`, `--action-primary`, full width in a column
  about 320px wide, the same as the auth forms), and at most one secondary (outline, `rounded-full`).
- Text is centred. No icon or illustration: monochrome, few elements, and nothing in a state colour,
  since this is information rather than a warning about the user's data.
- 16px side gutters on phones, no horizontal scroll at 375px, visible focus rings, 44px touch targets.

### 404, `app/not-found.tsx` (Server Component)

- Browser tab: `Page not found | FinTrack` (exported `metadata`).
- Label: **"Error 404"**
- Title: **"Page not found"**
- Text: **"The page you're looking for doesn't exist or may have moved."**
- Primary: **"Go to home"**, a link to `/`. The proxy sends `/` to `/dashboard` when signed in and to
  `/sign-in` when signed out (unit 1.2a), so the page never reads the session and stays static.

### Error, `app/error.tsx` (Client Component, as Next.js requires)

- Browser tab: `Something went wrong | FinTrack`, through React's `<title>` (error boundaries can't
  export `metadata`).
- Label: **"Error"**
- Title: **"Something went wrong"**
- Text: **"This page couldn't load. Try again, or go back to home."**
- Primary: **"Try again"**, calling the `retry` prop (stable since Next.js 16.3; it re-fetches and
  re-renders the segment). Not `reset`, which skips the re-fetch.
- Secondary: **"Go to home"**, a link to `/`.
- **Reference** (Question C): when the error has a `digest`, a line under the actions in
  `text-xs font-mono text-ink-muted`: "Reference: `<digest>`". The digest is a hash that matches the
  server log entry, so the owner can find the real error in Vercel's logs. Nothing else from the error is
  shown: never `error.message` or a stack, even though development builds include the message.
- Focus moves to the title when the page appears, so a screen reader announces it (the same rule as the
  auth forms' error alert).
- No logging in the browser. Server errors are already in Vercel's function logs with the same digest,
  and the browser only ever receives a generic message.

### Global error, `app/global-error.tsx` (Client Component)

- The same content and actions as `app/error.tsx`.
- It replaces the root layout, so it renders its own `<html lang="en">` and `<body>`, imports
  `globals.css`, and loads the Geist fonts. To share them, the two `next/font` declarations move from
  `app/layout.tsx` into `app/fonts.ts`, used by both. Without them the page would fall back to the
  browser's default serif font, because `--font-sans` points at the Geist variable.
- "Go to home" is a plain `<a href="/">` (a full page load), because the root layout itself failed.

## Checking the Error Page (Question B: the alternative)

A rendering error can't be triggered on purpose, and the owner chose not to ship a route that can.

- **Unit render tests** cover the three pages' content: the title, the actions, the reference, and that
  an error's message never appears (step 5).
- **One temporary check by the agent** (step 4): the agent adds a temporary `throw` to a page, builds,
  checks the real error page in a browser at desktop and phone width, in light and dark mode, then
  removes the `throw` and rebuilds. The `throw` is never committed, and `git diff` must show no trace of
  it before the unit is reported done.
- There is therefore **no browser test of the error page** after this unit, and no owner hand check of
  it. Phase 2's in-shell error page (Question A) can revisit this when real data pages can fail.

## Decisions

- **Standalone error pages for now; in-shell versions with Phase 2's first data page** (Question A).
- **"Go to home" links to `/`:** the proxy already chooses `/dashboard` or `/sign-in`, so the 404 page
  stays static and never reads the session.
- **Only the digest is shown:** never an error's message or stack (code-standards: never expose stack
  traces or provider errors).
- **No browser-side logging:** the server log already has the error under the same digest.
- **`retry`, not `reset`:** re-fetches the failed segment, which is what a temporary failure needs.
- **No on-demand error route** (Question B): nothing that can crash a page ships; the error page is
  covered by render tests and a one-off check.

## Rules to Follow

- Follow `ui-context.md` (tokens, radius, typography, focus, touch targets) and `code-standards.md`.
- Never show or log an error's message, a stack, tokens, cookies or personal details.
- Don't change the proxy's route rules or `lib/auth/paths.ts`.
- Never run anything against production. Don't edit `.env*` or `components/ui/*`.
- Don't commit until the owner says so.
