## Data Model

### The `transactions` table

```prisma
enum TransactionType {
  income
  expense

  @@map("transaction_type")
}

model Transaction {
  id          String          @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  userId      String          @map("user_id") @db.Uuid
  type        TransactionType
  amount      Decimal         @db.Decimal(19, 4)
  currency    String          @db.Char(3)
  occurredOn  DateTime        @map("occurred_on") @db.Date
  description String          @db.VarChar(100)
  createdAt   DateTime        @default(now()) @map("created_at") @db.Timestamptz(3)
  updatedAt   DateTime        @updatedAt @map("updated_at") @db.Timestamptz(3)

  @@index([userId, occurredOn(sort: Desc), createdAt(sort: Desc)])
  @@map("transactions")
}
```

- **Owner:** `user_id`, the Supabase auth user's ID, with no foreign key (Prisma doesn't model `auth`; account
  deletion removes rows in application code, Phase 12). The index serves the list's order and every
  `user_id` filter.
- **Type:** a Postgres enum through Prisma, so the client is typed. Only two values, and adding one later is a
  plain `ALTER TYPE … ADD VALUE`. `code-standards.md` gains the enum convention: PascalCase type, lower-case
  values, snake_case name through `@@map`.
- **Amount:** always above 0 (2.1, Question C); the type gives the direction. Stored exactly from 2.1's
  canonical string.
- **Date:** `occurred_on`, a calendar date (`date` itself is avoided as a column name, being a type name).
  No time of day.
- **Description:** what the transaction was, such as "Groceries" or "October salary" (Question D). It is the
  only label until 2.3 adds categories, and Phase 11 matches on it.
- **Not here:** `category_id` (2.3), tags (2.3), notes and attachments (2.5), a recurring rule's ID and its
  unique key (Phase 4). Each arrives with its own migration.
- **Migration** (`npx prisma migrate dev --create-only --name transactions`, then hand-added SQL):
  - `ALTER TABLE "transactions" ENABLE ROW LEVEL SECURITY;` (invariant 4; no policies).
  - `transactions_amount_range`: `CHECK ("amount" > 0 AND "amount" < 1000000000000)`.
  - `transactions_currency_format`: `CHECK ("currency" ~ '^[A-Z]{3}$')` (format only; the list is the
    app's, as for `profiles`).
  - `transactions_description_not_blank`: `CHECK (length(btrim("description")) > 0)`.
  - Decimal places per currency stay an app rule (2.1's table), not a database check.

## Validation

`lib/validation/transaction.ts` (new; shared by the form and the actions; no secrets):

| Field | Rule | Message |
| --- | --- | --- |
| `type` | `income` or `expense` | "Choose income or expense." |
| `amount`, `currency` | `moneyShape` and `withCanonicalAmount` (2.1) | 2.1's messages |
| `occurredOn` | `YYYY-MM-DD`, a real calendar date, from 2000-01-01 to one year after today (Question C) | "Enter a date." / "Enter a date from 1 Jan 2000." / "Enter a date no more than a year ahead." |
| `description` | trimmed; 1 to 100 characters; no control characters | "Enter a description." / "Use at most 100 characters." / "Remove line breaks and tabs." |

- **All errors at once.** Unit 2.1's notes flagged that its amount check only runs once every other field
  passes, so an amount error would appear only after the description was fixed. Here the amount check runs
  whenever the currency is valid, whatever the other fields say (Zod 4's `when` option on the refinement,
  confirmed in step 1), so one submit shows every problem. 2.1's `moneySchema` is unchanged.
- **"One year after today"** uses the server's UTC date, which is generous enough at any time zone; it only
  catches typos such as 2062. The browser's form uses the same rule with its own date.
- Accepts its own output (`code-standards.md`): parsing the parsed values again gives the same result.
- `transactionIdSchema`: a UUID (`z.uuid()`), checked before any query, so a malformed ID never reaches
  Postgres (which would raise an error rather than find nothing).

## Data Layer

`lib/db/transactions.ts` (new, `server-only`; the only code that touches `transactions`):

```ts
export interface TransactionView {
  id: string;
  type: "income" | "expense";
  amount: string;     // 2.1's canonical string, with the currency's decimal places ("1234.50", "1500")
  currency: string;
  occurredOn: string; // "YYYY-MM-DD"
  description: string;
}

export async function listRecentTransactions(userId: string, limit: number): Promise<{ items: TransactionView[]; hasMore: boolean }>;
export async function getTransaction(userId: string, id: string): Promise<TransactionView | null>;
export async function createTransaction(userId: string, input: TransactionValues): Promise<TransactionView>;
export async function updateTransaction(userId: string, id: string, input: TransactionValues): Promise<TransactionView | null>;
export async function deleteTransaction(userId: string, id: string): Promise<boolean>;
```

- Every query filters on `userId` **and** `id`: reads with `findFirst({ where: { id, userId } })`; writes
  with `updateMany` / `deleteMany` on `{ id, userId }`, where a count of 0 means "not found" (missing or
  another user's, which look the same). `updateTransaction` then reads the row back. Step 1 checks whether
  Prisma 7's `update({ where: { id, userId } })` is simpler and as safe.
- `userId` only ever comes from the verified session (invariant 3).
- `Decimal` → `amount.toFixed(currencyDecimals(currency))` (`code-standards.md`); a code no longer in the list
  (only if the list shrinks) uses 2 places, and the edit form asks for a supported currency.
- Dates: written as `new Date("<YYYY-MM-DD>T00:00:00.000Z")`, read back as the UTC date's first 10
  characters, so no time zone ever shifts a day. Step 1 confirms the round trip through the `pg` adapter.
- The list asks for `limit + 1` rows to know whether more exist. Order: `occurred_on` descending, then
  `created_at` descending (the newest entry first within a day).
- Not cached (invariant 9).

## Server Actions

`app/(app)/transactions/actions.ts` (new). Each is a public endpoint: `getSignedInUser()` first (`null` while
signed out or while 2FA is owed, invariant 6), then Zod, then the data layer with the session's user ID.

| Action | Input | On success |
| --- | --- | --- |
| `createTransaction(input)` | the form's values | redirect to `/transactions?done=added` |
| `updateTransaction(id, input)` | the ID from the page, the form's values | redirect to `/transactions?done=updated` |
| `deleteTransaction(id)` | the ID from the page | redirect to `/transactions?done=deleted` |

| Code | When | Message |
| --- | --- | --- |
| `NOT_SIGNED_IN` | No session, or 2FA owed | "Your session has ended. Sign in again." |
| `INVALID_INPUT` | Zod failure (with `fieldErrors`) | "Check the highlighted fields." |
| `NOT_FOUND` | Malformed ID, missing, or another user's | "This transaction no longer exists." |
| `SAVE_FAILED` | Create or update throws | "Couldn't save this transaction. Try again." |
| `DELETE_FAILED` | Delete throws | "Couldn't delete this transaction. Try again." |

- Redirecting from the action means the list renders fresh, with no `refresh()` needed; the form never needs
  the saved values back.
- An `id` or `userId` inside the input is ignored (the schema strips unknown keys).
- **Shared result module:** `lib/actions/result.ts` (new; no secrets, not server-only): the
  `ActionResult<T>` type, a `failure(code, message, fieldErrors?)` helper and `logActionError(scope, action,
  error)`, which logs only the error's `name` and a Prisma `P####` code. `updateProfile` moves to it with no
  change in behaviour or messages; each action file keeps its own codes and messages.
- Never logged: amounts, currencies, descriptions, dates, IDs or the user's ID.

## Questions for the Owner

Answered: **A to F, the recommended options** (2026-11-27).

- **A. Create and edit: separate pages or a dialog?** **Recommended: separate pages**
  (`/transactions/new`, `/transactions/[id]/edit`). The form is short today, but 2.3 adds category and tags
  and 2.5 adds notes and a receipt upload, which `ui-context.md` puts on a page. Pages also have their own
  URLs (back button, a link to one transaction), work before JavaScript loads, and give the in-shell 404 a
  real use. Alternative: a dialog on `/transactions`, fewer page loads now, likely moved to a page in 2.5.
- **B. How is "today" decided for a new transaction's date?** **Recommended: the browser's own date**, with
  no time zone setting. You type the date in the form anyway; the default only saves a tap, and your browser
  knows your local day (Asia/Singapore). A time zone setting is needed first by Phase 4's daily posting job,
  which decides it then. Alternative: a time zone field on the Profile page now, used for the default date.
- **C. Which dates are allowed?** **Recommended: from 1 Jan 2000 to one year ahead.** Future dates are
  allowed (a bill you already know about), and the limits only catch typos. Alternatives: no future dates
  (the server then has to guess your time zone near midnight), or no limits.
- **D. Description: required, and how long?** **Recommended: required, up to 100 characters.** Until 2.3's
  categories it is the only way to tell transactions apart in the list, and Phase 11 matches on it.
  Alternative: optional, with the list showing "Expense" or "Income" when it is empty.
- **E. What does the list show before 2.4?** **Recommended: the 50 most recent**, newest first, each row
  opening its edit page, with a note when more exist. 2.4 replaces it with the full history, filters and
  paging. Alternative: every transaction, unpaged (fine for a few hundred rows, slow later).
- **F. How does the app confirm a change?** **Recommended: a status line on the list** ("Transaction
  added.", "Changes saved.", "Transaction deleted."), from a short-lived `?done=` parameter that the page
  removes, as `/sign-in?error=google` does. No new dependency. Alternative: toasts with shadcn's `sonner`
  (a new dependency, which every later feature could reuse).

## Decisions

- **Amounts are positive; the type carries the direction:** as 2.1 decided, so sums by type need no sign
  checks.
- **Calendar dates, written and read as UTC dates:** the stored day is the day typed, in any time zone.
- **Delete is permanent, after a confirmation:** no soft delete, so a deleted row is really gone (matches
  Phase 12's account deletion). 2.5 adds removing the transaction's receipt files with it.
- **Missing and another user's transactions look the same:** 404 on pages, `NOT_FOUND` in actions, so a
  transaction's existence is never revealed.
- **No totals before conversion:** adding different currencies would give a wrong number.
