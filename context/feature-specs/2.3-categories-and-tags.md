## Goal

Today a transaction has only a description to say what it was. After this unit the user can **give each
transaction a category and any number of their own tags** (goal 1; `project-overview.md` → "Add, edit and
delete transactions with categories such as salary, rent and groceries" and "Custom tags on transactions"):

- A `categories` table: each user's own categories, one set for expenses and one for income, starting from a
  ready-made list (Questions A and B). The transaction form offers the categories of the chosen type.
- A `tags` table and a `transaction_tags` link table: the user types tags in the form, new ones are created
  on save, and earlier ones are suggested (Questions D and E).
- `transactions.category_id`, optional (Question C). Existing transactions keep working with no category and
  no tags.
- The list shows each row's category (Question F); the edit page shows its category and tags.
- The database itself refuses a link between one user's transaction and another user's category or tag, and
  the cross-user test grows to cover all three new tables (success criterion 9).

This unit lays the ground for later phases that read categories and tags: 2.5's filters by category and tag,
Phase 6's budgets per category, Phase 8's reports by category or tag, and Phase 11's automatic
categorization. Managing categories (add, rename, delete) is Phase 14's "custom categories" (Question A).

## What the Source Documents Ask For

- **High-level Requirements:** "Add Income/Expense: … categorizing them (e.g., salary, rent, groceries)";
  "Custom Tags: Allow users to create and apply custom tags to transactions for better organization";

  date range, categories, or tags"; "Personalization Options: Users can customize their dashboard,
  categories, and themes".
- **User Story:** "categorized by type (e.g., salary, rent, groceries), so I can keep track of where my money
  comes from and where it goes"; "add custom tags to my transactions … so I can easily filter and find
  specific types of spending".
- **Functional Design:** "Filters for transaction history by date, category, or tags"; "custom tags" under
  Customization.
- **`project-overview.md`:** Release 1 has categories and custom tags; Release 2's Phase 14 has "custom
  categories". `architecture.md`'s storage model already lists `categories`, `tags` and `transaction_tags`.

So in Release 1 categories are a ready-made list, tags are the user's own, and adding your own categories
waits for Phase 14.

## Data Model

### `categories`

```prisma
model Category {
  id        String          @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  userId    String          @map("user_id") @db.Uuid
  type      TransactionType
  name      String          @db.VarChar(40)
  createdAt DateTime        @default(now()) @map("created_at") @db.Timestamptz(3)
  updatedAt DateTime        @updatedAt @map("updated_at") @db.Timestamptz(3)

  transactions Transaction[]

  @@unique([id, userId, type]) // the target of the transactions' composite foreign key
  @@index([userId, type])
  @@map("categories")
}
```

- **Per user, not shared** (Question A): each user has their own rows, so Phase 6's budgets and Phase 11's
  rules point at a category ID, and Phase 14's custom categories (add, rename, delete) need no data
  migration. There is no shared reference table.
- **Type:** reuses unit 2.2's `transaction_type` enum. An expense can only have an expense category, and an
  income an income category.
- **Starter set:** the first time the user's categories are read and they have none, the data layer inserts
  the starter list (Question B) in one statement (`createMany` with `skipDuplicates`, so two pages loading at
  once can't create it twice: the unique name index below makes the second insert a no-op). This is a write
  during a read, unlike `profiles` (whose defaults need no row), because a transaction needs a real category
  ID to point at. Phase 14, which lets the user delete categories, must stop re-seeding a user who deleted
  them all (a note for that phase).
- **Names:** 1 to 40 characters, trimmed, unique per user and type ignoring case.
- **Migration SQL (hand-added):** RLS on; `categories_name_not_blank`
  (`CHECK (length(btrim("name")) > 0)`); a unique index `categories_user_id_type_name_key` on
  (`user_id`, `type`, `lower("name")`), which Prisma can't express (an expression index), so it lives only in
  the migration and a comment in the schema.

### `tags`

```prisma
model Tag {
  id        String   @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  userId    String   @map("user_id") @db.Uuid
  name      String   @db.VarChar(30)
  createdAt DateTime @default(now()) @map("created_at") @db.Timestamptz(3)

  transactions TransactionTag[]

  @@unique([id, userId]) // the target of the links' composite foreign key
  @@index([userId])
  @@map("tags")
}
```

- The user's own words ("holiday-2026", "work", "reimbursable"). Created when a transaction using a new name
  is saved; matched to an existing tag ignoring case, keeping the first spelling ("Work" and "work" are one
  tag).
- No `updatedAt`: a tag is never changed in this unit (no rename; Phase 14).
- **Migration SQL (hand-added):** RLS on; `tags_name_not_blank`; a unique index `tags_user_id_name_key` on
  (`user_id`, `lower("name")`).
- **Unused tags** (Question D): when a save or a delete leaves a tag on no transaction, it is deleted in the
  same database transaction, so suggestions only show tags in use and no tag-management page is needed yet.

### `transaction_tags`

```prisma
model TransactionTag {
  transactionId String @map("transaction_id") @db.Uuid
  tagId         String @map("tag_id") @db.Uuid
  userId        String @map("user_id") @db.Uuid

  transaction Transaction @relation(fields: [transactionId, userId], references: [id, userId], onDelete: Cascade)
  tag         Tag         @relation(fields: [tagId, userId], references: [id, userId], onDelete: Cascade)

  @@id([transactionId, tagId])
  @@index([userId, tagId])
  @@map("transaction_tags")
}
```

- **Its own `user_id`** (invariant 3: every user-owned row has one). Both foreign keys include it, so a link
  can only join a transaction and a tag of the **same** user: the database refuses anything else, whatever
  the app does.
- Deleting a transaction (or a tag) removes its links (`Cascade`). The primary key stops a tag being added to
  a transaction twice.
- RLS on (hand-added).

### `transactions` (changed)

```prisma
model Transaction {
  // … unit 2.2's fields …
  categoryId String?   @map("category_id") @db.Uuid
  category   Category? @relation(fields: [categoryId, userId, type], references: [id, userId, type], onDelete: Restrict)
  tags       TransactionTag[]

  @@unique([id, userId]) // the target of the links' composite foreign key
  @@index([userId, categoryId])
  // … unit 2.2's index and @@map …
}
```

- **One composite foreign key** (`category_id`, `user_id`, `type`) → `categories` (`id`, `user_id`, `type`):
  a transaction can only point at **its own user's** category of **its own type**. With `category_id` null
  (no category), Postgres skips the check (`MATCH SIMPLE`), which is what we want.
- **`onDelete: Restrict`:** nothing deletes a category in this unit. Phase 14 decides what deleting one does
  (likely `SET NULL (category_id)`, a Postgres 15+ column list Prisma can't write, so hand-added SQL then).
  A plain `SetNull` would try to null `user_id` and `type` too, so it is never used here.
- **Changing a transaction's type** while it has a category of the old type: the form clears the category
  when the type changes, and the action refuses a mismatch with a field error; the foreign key is the last
  guard.
- The extra unique on (`id`, `user_id`) and on `categories` (`id`, `user_id`, `type`) are redundant with the
  primary keys but required by Postgres as foreign-key targets. They cost one small index each.
- Step 1 confirms Prisma 7.10.1 accepts a relation whose fields mix the optional `categoryId` with the
  required `userId` and `type`. **If it doesn't**, the relation becomes `categoryId` → `categories.id` in
  Prisma, the composite foreign key is hand-added SQL in the migration instead, and the spec's behaviour is
  unchanged (report before building, as for every step 1 finding).

### Migration

One migration, `categories_tags` (`npx prisma migrate dev --create-only --name categories_tags`, then the
hand-added SQL above): three new tables with RLS on and no policies, the two expression indexes, the two
name checks, `transactions.category_id` and the composite foreign keys. Existing rows get `category_id` null
and no tags; nothing is backfilled.

## Validation

`lib/validation/transaction.ts` (changed) gains two fields; everything from 2.2 is unchanged.

| Field | Rule | Message |
| --- | --- | --- |
| `categoryId` | `null` (no category), or a UUID; `""` from the select becomes `null` (Question C) | "Choose a category from the list." |
| `tags` | an array of names, at most 10 after removing duplicates (ignoring case) | "Use at most 10 tags." |
| each tag | trimmed; 1 to 30 characters; no control characters and no commas | "Use at most 30 characters in a tag." / "Remove commas, line breaks and tabs from tags." |

- Empty tag names are dropped, and duplicates that differ only in case keep the first spelling, so
  `["Work", " work ", ""]` becomes `["Work"]`. The output is sorted only for display, not here.
- **Category of the other type, another user's, or one that doesn't exist:** the schema can't know, so the
  action asks the data layer, which answers "not one of yours of this type"; the action returns
  `INVALID_INPUT` with that field error (not `NOT_FOUND`, which stays for the transaction itself).
- Still accepts its own output, and still shows every field error in one submit (`when`, no `abort`; unit
  2.2's rule in `code-standards.md`).
- `lib/validation/tag.ts` isn't needed: tag rules live beside the transaction's fields, their only user.

## Data Layer

- **`lib/db/categories.ts`** (new, `server-only`; the only code that touches `categories`):

  ```ts
  export interface CategoryView { id: string; type: "income" | "expense"; name: string }
  export async function listCategories(userId: string): Promise<CategoryView[]>; // seeds the starter set if the user has none
  export async function findCategory(tx: TxClient, userId: string, id: string, type: TransactionType): Promise<CategoryView | null>;
  ```

- **`lib/db/tags.ts`** (new, `server-only`; the only code that touches `tags`):

  ```ts
  export async function listTagNames(userId: string): Promise<string[]>; // for the form's suggestions, sorted
  export async function resolveTags(tx: TxClient, userId: string, names: string[]): Promise<string[]>; // tag IDs; creates missing ones
  export async function deleteUnusedTags(tx: TxClient, userId: string): Promise<void>;
  ```

  `resolveTags` reads the user's tags matching the names (case-insensitive), creates the missing ones with
  `createMany({ skipDuplicates: true })` (the unique index absorbs a race), and reads again.
- **`lib/db/transactions.ts`** (changed; still the only code that touches `transactions`, and now also
  `transaction_tags`, since links only change as part of a transaction's save):
  - `TransactionView` gains `category: { id: string; name: string } | null` and `tags: string[]` (names,
    sorted case-insensitively).
  - `createTransaction` and `updateTransaction` run in **one interactive database transaction**: check the
    category (`findCategory`), resolve the tags, write the row, replace its links (`deleteMany` then
    `createMany`), delete unused tags. A category that isn't the user's of that type returns
    `{ error: "category" }` without writing anything. `updateTransaction` still answers `null` for a
    missing or another user's transaction.
  - `deleteTransaction` deletes the row (links go by `Cascade`) and then unused tags, in one transaction.
  - `listRecentTransactions` and `getTransaction` include the category name and tag names in the same query
    (`select` with the relations; no N+1).
- `TxClient` is the interactive transaction's client type, exported from `lib/db/client.ts`'s module so it
  never leaves `lib/db`.
- Every query still filters on `userId`, and single-row ones on `id` and `userId` together.
- Step 1 confirms interactive transactions work through the `pg` adapter on the **transaction pooler**
  (`?pgbouncer=true`, port 6543), on development. If they don't, stop and report: the fallback is a batch
  `$transaction([...])` with the reads done first, which loses the race guard on unused-tag deletion only.

## Questions for the Owner

- **A. Where do categories come from in Release 1?** **Recommended: each user's own `categories` rows,
  started from a ready-made list, with no way to edit them until Phase 14** ("custom categories" is a
  Release 2 item). Budgets and rules can point at a category ID from the start, and Phase 14 only adds
  screens. Alternatives: a fixed list in code, stored on the transaction as a short code (simplest now, but
  Phase 14 then has to move every transaction to real rows); or a small Settings section to add and rename
  categories now (pulls part of Phase 14 forward).
- **B. Is the starter list right?** **Recommended: the list in Starter Categories** (14 expense, 6 income,
  each ending in Other). Tell me any names to add, drop or rename; it's easy to change before the first
  production save, and harder after (renaming rows then needs a migration).
Answered on 2026-11-27: **A to F, the recommended options.** C was first answered "required", then changed
back to optional the same day (owner's decision, when Accounts became its own unit).

- **C. Is a category required?** **Recommended: optional, with "No category" first in the list.** Your
  existing transactions have none, a quick entry stays one step shorter, and Phase 11's automatic
  categorization fills it in later. Alternative: required for new and edited transactions (budgets then
  count everything, but every existing transaction must be given one when next edited).
- **D. What happens to a tag no transaction uses any more?** **Recommended: it is deleted automatically**, in
  the same save or delete, so the suggestions only show tags you use and no tag page is needed yet.
  Alternative: keep every tag ever typed (suggestions grow; deleting them waits for Phase 14).
- **E. Tag limits?** **Recommended: up to 10 tags per transaction, up to 30 characters each, matched ignoring
  case** (the first spelling is kept, so "Work" and "work" are one tag). Alternatives: case-sensitive tags, or
  other limits.
- **F. Where do category and tags show before 2.5?** **Recommended: the category on each list row, tags only
  on the edit page**, so rows stay readable at phone width; 2.5's history table adds a tag column and
  filters. Alternative: tags as small chips on the list rows now (a second line on phones).

## Decisions

- **The database refuses cross-user links, not only the app:** every foreign key between user-owned rows
  includes `user_id`, so even a bug in the data layer can't attach one user's tag or category to another
  user's transaction.
- **A category belongs to one type:** an expense can't be filed under Salary; the composite foreign key
  includes `type`.
- **Tags are created by use:** no separate "create tag" step or action; a tag exists while a transaction uses
  it (Question D).
- **Saving a transaction is atomic:** the row, its category check, its tags and its links change together or
  not at all.
- **No backfill:** existing transactions keep no category; nothing guesses one.

## Rules to Follow

- Follow `architecture.md` and `code-standards.md`: the user ID only from the session, Zod before any logic,
  Prisma only inside `lib/db`, RLS on with no policies, no `db push`, no edits to applied migrations.
- Never log category names, tag names, descriptions, amounts, dates, IDs or emails, including in CI's public

- Never run anything against production. Don't edit `.env*` or `components/ui/*`; no new dependency without

## Implementation Notes (2026-11-27)

- Built as specified, with the differences below. No proxy, auth, cron, `vercel.json`, Supabase, Vercel or
  env change; no new dependency and no new shadcn component.
- **Step 1 findings** (Prisma 7.10.1 against development, with a temporary probe that left no rows):
  - The composite relation on (`categoryId`, `userId`, `type`) with only `categoryId` optional validates,
    so the spec's SQL fallback wasn't needed. Prisma's default `ON UPDATE CASCADE` on it would let a change
    to a category's `type` rewrite its transactions' type, so the relation is `onUpdate: Restrict` too.
  - `createMany({ skipDuplicates: true })` against the `lower(name)` expression index treats "work" as a
    duplicate of "Work"; two simultaneous seeds create one set; an interactive transaction works through
    the transaction pooler and rolls back; the composite foreign key refuses an expense pointing at an
    income category (P2003).
  - `migrate dev --create-only` stops in a non-interactive shell when Prisma prints a warning (a unique
    constraint on `[id,user_id]` will be added). The migration SQL was generated with `migrate diff
    --from-config-datasource --to-schema` instead, written to `20261127115351_categories_tags`, the
    hand-added SQL appended, and applied with `migrate dev`. Development check (read-only query): six
    tables, all owner `prisma`, RLS on and not forced, grants for `prisma` only, no policies; the two name
    checks, the three composite foreign keys and the two `*_name_key` expression indexes present.
- **Fewer round trips than specified.** A query from this laptop to the development pooler takes about
  300ms, so the first build's save with tags (about 11 round trips) took over 3 seconds, near Prisma's
  5-second interactive-transaction limit. Changes:
  - No `findCategory` read: the composite foreign key is the check, and its violation (P2003) on the
    transaction write becomes `{ error: "category" }` (the write throws out of the database transaction, so
    it rolls back). `lib/db/categories.ts` exports only `listCategories`.
  - `resolveTags` is one `createMany` (`skipDuplicates`) and one read, not read, create, read. It matches
    names against the user's tags in code, not with Prisma's case-insensitive `in` (which may become
    `ILIKE`, where `_` and `%` are wildcards); a database test covers `50%_off`.
  - A new transaction with no tags is one query, with no interactive transaction; a new one with tags skips
    the link delete and unused-tag clean-up, which can't apply to a new row.
  - Interactive transactions set `timeout: 15_000` (on Vercel, next to the database, a save takes
    milliseconds).
- **A unit 2.2 bug, found by this unit's browser test and fixed here:** reopening a transaction's edit page
  through a link after saving it showed the values from before the save, and `/transactions/new` would
  reopen with the last draft. Cache Components keep up to three visited routes mounted in React's
  `<Activity>`, with their state, and `useForm` reads `defaultValues` only once. `revalidatePath` didn't
  help (tried and removed). Fix, as Next's preserving-ui-state guide recommends: each server render gives
  the form a fresh key (`crypto.randomUUID()` in `transaction-form-card.tsx`), so a link visit starts from
  the server's values and back/forward still restore a draft. The browser test now opens the second form by
  link and reopens an edited transaction. Production has this bug until this unit is merged.
