## Goal

Today every app page opens for anyone, signed in or not; `proxy.ts` only refreshes the session. After
this unit:

- A signed-out visitor who opens any app page (for example `/budgets`) is sent to the sign-in page, and
  comes back to that page after signing in.
- `/` is the entry point (owner's choice on 2026-11-17, Option A): signed out, it goes to `/sign-in`;
  signed in, it goes to `/dashboard`. The sign-in and sign-up pages keep their own URLs.
- A signed-in user who opens the sign-in, sign-up or forgot-password page goes to the dashboard.
- Server code has one helper, `requireUser()`, that every protected page and data function will use to
  get the user. Unit 1.4 adds the 2FA (`aal2`) check there.

The proxy is still not the authorization boundary (architecture: Auth and Access Model). It decides
where a browser goes; server code that reads or changes data checks the session itself.

## Route Rules

The proxy applies these rules to `GET` and `HEAD` requests. "Signed in" means `getClaims()` in the
proxy returned valid claims.

| Path | Signed out | Signed in |
| --- | --- | --- |
| `/` | Redirect to `/sign-in` | Redirect to `/dashboard` |
| `/sign-in`, `/sign-up`, `/forgot-password` (guest pages) | Show the page | Redirect to the safe `next`, or `/dashboard` |
| `/reset-password`, `/check-email`, `/auth-error` (open pages) | Show the page | Show the page |
| `/auth/*` (email links now, unit 1.3's OAuth callback later) | Pass through | Pass through |
| `/api/*` | Pass through (each route checks its own auth) | Pass through |
| Anything else: app pages, and unknown paths | Redirect to `/sign-in?next=<path and query>` | Show the page |

Notes on the table:

- **`/reset-password` must stay open to signed-in users.** A reset link signs the browser in, so a
  "signed-in users leave auth pages" rule would send the user to the dashboard before they set a new
  password. This would break units 1.1a and 1.1b.
- **`/check-email` and `/auth-error` stay open** to both states. Nothing on them depends on the session.
- **Anything not listed is protected (default deny).** A new page is protected without anyone
  remembering to add it. A signed-out visit to an unknown path goes to sign-in first, then shows the
  404 after sign-in. That is acceptable.
- **`/api/cron/*` never reaches the proxy** (its matcher leaves it out, as now). Other `/api/*` routes
  (exports, in later phases) answer `401` themselves rather than being redirected to an HTML page.
- **Only `GET` and `HEAD` are redirected.** Server Action calls are `POST` requests to the current
  page's path. Redirecting them would break the action call, and each action already checks auth
  (invariant 5). For example, `signOut` on an expired session still reaches the action and ends on
  `/sign-in`.
- **The proxy redirects with `307`**, and copies any refreshed session cookies and Supabase's
  no-cache headers onto the redirect. Supabase's guide warns that a redirect without the refreshed
  cookies can sign the user out.

## Return to the Requested Page (`next`)

- A signed-out visit to `/budgets?month=2026-11` redirects to `/sign-in?next=%2Fbudgets%3Fmonth%3D2026-11`.
- The sign-in page passes `next` to the form, and the `signIn` action receives it as part of its input.
  After a successful sign-in, the action redirects to `safeReturnPath(next)`.
- A signed-in visit to `/sign-in?next=...` also goes to `safeReturnPath(next)`.
- **`safeReturnPath(value)`** (new, `lib/auth/redirect.ts`) returns the value only when **all** of these
  hold; otherwise it returns `/dashboard`:
  - it is a string of at most 2048 characters with no control characters or backslashes;
  - it starts with exactly one `/` (not `//`);
  - resolved against a fixed placeholder origin, it keeps that origin (so it can't point to another
    site);
  - its path isn't `/`, a guest page, an open page, or under `/auth/` or `/api/`. Returning to them
    makes no sense, and a guest page would loop.
  - It returns the path and query only, never a fragment.
- `safeNextPath` (the email-link allowlist) is unchanged. Email links still only accept `/dashboard` and
  `/reset-password`.
- Only sign-in carries `next`. Sign-up ends on the check-email page and its link goes to `/dashboard`
  (unit 1.1a), so `next` is dropped there. The "Sign up" link on the sign-in page doesn't forward it.

## Session Helpers (`lib/auth/session.ts`)

- `getCurrentClaims()` stays as it is: the user or `null`, never cached.
- **`requireUser()` (new):** returns the `CurrentUser`, or calls `redirect("/sign-in")` when there is
  none. It is for Server Components and pages, as a second line behind the proxy (for example, when a
  session expires between the proxy and the render). It is the single place unit 1.4 will add the
  `aal2` check.
- Server Actions keep using `getCurrentClaims()` and return an error result rather than redirecting,
  as `updatePassword` does today. Phase 2's data actions will add a general "not signed in" error code;
  this unit adds none, because no data action exists yet.
- **`AccountArea`** (the header's account menu) uses `requireUser()`. Its signed-out "Sign in" link is
  removed, because a signed-out browser can no longer reach an app page. The page header's right
  padding (`pr-24`, sized for that link) shrinks to fit the 44px avatar button (see Question C).

## Scope

**In scope**

- `lib/auth/routes.ts` (new): the path lists and a pure function, `routeDecision({ pathname, search,
  method, signedIn })`, returning "pass" or a redirect target. The proxy calls it; unit tests cover it
  without a request.
- `lib/auth/proxy-session.ts`: `refreshSession` also returns whether the browser is signed in, plus a
  helper to build a redirect that carries the refreshed cookies and headers.
- `proxy.ts`: applies `routeDecision`. The matcher is unchanged.
- `lib/auth/redirect.ts`: `safeReturnPath`.
- `lib/auth/session.ts`: `requireUser()`.
- `app/(auth)/actions.ts`: `signIn` accepts an optional `next` and redirects to `safeReturnPath(next)`.
  The other actions are unchanged (`signOut` still ends on `/sign-in`).
- `lib/validation/auth.ts`: the action-side schema for `next` (an optional string; `safeReturnPath`
  does the real check).
- `app/(auth)/sign-in/page.tsx` and `components/auth/sign-in-form.tsx`: pass `next` from the URL to
  the action.
- `app/page.tsx`: stays as a fallback redirect to `/dashboard` (the proxy handles `/` first). The
  comment is updated.
- `components/app-shell/account-area.tsx` and `components/app-shell/page-header.tsx`: the header changes
  above.
- Tests (step 5) and docs (step 7).

**Out of scope**

- Google and Facebook sign-in, and the OAuth callback (unit 1.3). The `/auth/*` rule already covers it.
- 2FA and `aal2` checks (unit 1.4). `requireUser()` is where they will go.
- A landing or marketing page at `/`. `/` only redirects.
- Showing the sign-in form at `/` itself (Option B, not chosen).
- Running Supabase's local stack in CI. Its decision is still due before unit 1.4.
- Any change to the email links, the reset-pending cookie or the check-email wording.
- Ending sign-out on `/` instead of `/sign-in`. They now lead to the same place, so it stays as it is.

### 2. Routing logic (`lib/auth/routes.ts`) and `safeReturnPath`

- One list each for guest pages, open pages, and the passed-through prefixes (`/auth/`, `/api/`).
  Each list has a comment pointing to this spec.
- `routeDecision` implements the Route Rules table exactly, including "only `GET` and `HEAD`". It
  builds `next` from the path and query, URL-encoded.
- `safeReturnPath` in `lib/auth/redirect.ts`, as specified, sharing the page lists from `routes.ts` so
  the two can't drift apart.

### 3. Proxy

- `refreshSession` keeps its rule that nothing runs between creating the client and `getClaims()`. It
  returns `{ response, signedIn }`, where `signedIn` is true only when `getClaims()` returned claims with
  no error.
- A helper builds a `307` redirect to a same-origin URL and copies every cookie and header that
  `setAll` put on `response`.
- `proxy.ts` calls `routeDecision` and returns either the refreshed response or the redirect. The
  matcher stays the same, so `/api/cron/*`, `_next` assets and image files never reach it.
- If Supabase can't be reached while verifying a session, `getClaims()` fails and the browser counts as
  signed out (fails closed). Nothing new is logged; tokens and cookies are never logged.

### 4. Session helper, sign-in `next`, header

- `requireUser()` in `lib/auth/session.ts`, built on `getCurrentClaims()`. Not cached (invariant 9).
- `signIn`: the input gains an optional `next`. Zod validates the shape before any other work, and
  `safeReturnPath` decides the target. Wrong credentials still return the same single message.
- The sign-in page reads `next` from the URL and passes it to `SignInForm`, which sends it with the
  email and password. It is never shown on the page.
- `AccountArea` uses `requireUser()` and always renders `UserMenu`. `page-header.tsx`'s padding shrinks
  to fit the avatar button, and the comment explaining `pr-24` is updated (Question C).
- `app/page.tsx` keeps `redirect("/dashboard")` as a fallback, with a comment that the proxy handles

## Decisions

- **`/` redirects rather than showing the sign-in form (Option A):** owner's choice on 2026-11-17. Every
  existing link to `/sign-in` keeps working, and the 1.1a pages are unchanged.
- **Protected by default:** only the listed guest and open pages are public, so a new page can't be
  left open by accident.
- **The proxy redirects; server code authorizes:** as `code-standards.md` already requires.
  `requireUser()` is the second line for pages, and actions check the session themselves.
- **Only `GET` and `HEAD` are redirected:** Server Actions are `POST`s and authorize themselves.
- **`safeReturnPath` is separate from `safeNextPath`:** email links keep their two-item allowlist; the
  sign-in return path accepts any same-origin app page, with the rules above.
- **No new error code yet:** a general "not signed in" action error arrives with Phase 2's first data
  action.

## Rules to Follow

- Follow `architecture.md` and `code-standards.md`, especially the Auth rules: `getClaims()` (through

- `proxy.ts` must not run on, or redirect, `/api/cron/*`.

## Implementation Notes (2026-11-17)

- Built as specified, with the differences below. No schema, migration, Supabase or Vercel change.
- **Step 1 findings:** the bundled docs confirm that `redirect()` inside a streamed Suspense boundary
  sends the redirect to the browser (a meta tag), so `AccountArea` can use `requireUser()`. Server
  Functions are `POST`s to the page's route. Next.js strips its internal `_rsc` parameter from
  `request.nextUrl` before the proxy runs, so it never ends up in `next`. `@supabase/ssr` passes
  `Cache-Control`, `Expires` and `Pragma` to `setAll`, and `redirectWithSession` copies exactly those.
- **`next` is read by the form at submit time, not by the page.** Reading `searchParams` in the page
  would put the form behind a Suspense fallback, taking it out of the static shell, so it would flash
  in. `SignInForm` reads `next` from `window.location.search` when it submits and sends it to `signIn`.
  The behaviour is the one specified, and `/sign-in` is still fully static in the build.
- **`lib/auth/paths.ts` (new):** holds the guest, open and passed-through lists. Both `routes.ts`
  (which imports `safeReturnPath`) and `redirect.ts` read them, so keeping them in `routes.ts` would
  have made an import cycle.
- **`signInActionSchema`:** a bad `next` (not a string) is dropped with `.catch(undefined)` rather
  than failing the sign-in; `safeReturnPath` decides the target.
- **Playwright:** `playwright.config.ts` reads the two test-account values with Node's
  `util.parseEnv` instead of `@next/env`, because `loadEnvConfig` would load every `.env.local` value
  into the test process. `E2E_PORT` (default 3000) is new, so a local run can use port 3100 beside the
  owner's dev server. `tests/e2e/auth-state.ts` holds the shared session path and the sign-in steps.
- **The header test moved** from `auth-pages.spec.ts` (signed out, "Sign in" link) to
  `app-shell.spec.ts` (signed in, "Account menu" button), and checks that no "Sign in" link remains.
  The header's padding is now `pr-14`.
- **Results:** `npm test` 284 passed (12 files); lint, typecheck and build pass. Playwright on port
  3100 with the test account: 92 passed, 15 skipped (the existing desktop-only and phone-only splits,
