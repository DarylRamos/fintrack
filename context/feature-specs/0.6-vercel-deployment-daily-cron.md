## Goal

Put FinTrack on the internet and give it a daily scheduled job before any feature needs one. When this
unit is done:

- the `main` branch deploys to Vercel Hobby as the production site, with functions in Sydney (`syd1`),
  next to both Supabase projects, and on Node 24, matching `.nvmrc`;
- production reads the production Supabase project through `DATABASE_URL`, set only in Vercel;
- a Vercel **Schedule** named `heartbeat` calls `POST /api/cron/heartbeat` once a day. The route refuses
  any request without the `CRON_SECRET` bearer token, then checks the database with a read-only
  `SELECT 1`;
- the shared pieces later scheduled jobs need (the secret check, the route conventions, the
  `vercel.json` setup and the docs) are in place, so Phase 3 (exchange rates) and Phase 4 (recurring
  transactions) only add their own schedule and route.

The route stores nothing and changes nothing. Whether its daily query keeps the free Supabase project
from pausing is unit 0.7's question; this unit only gives 0.7 a daily query to observe.

## Why a Scheduled Route in This Unit

Deploying doesn't need a scheduled job. The two are in one unit because a scheduled job only runs on a
real deployment, so this is the first point where it can be built and proven. It's set up now, before
any feature needs it, for four reasons:

1. **Later phases depend on it.** Phase 3 fetches exchange rates every day and Phase 4 posts recurring
   transactions every day. Vercel Schedules is what wakes the app up to do that, since nobody is
   clicking anything at that time. Setting up the scheduling and its security now, with a job that does
   almost nothing, means those phases only add their own logic.
2. **It proves production works at runtime.** The build proves the code compiles. The daily `SELECT 1`
   proves the deployed app can reach the production database with the production string, every day,
   which nothing else checks until Phase 1.
3. **It may keep the production database awake.** Supabase pauses free projects after 7 days of low
   activity. A daily query might count as activity; unit 0.7 checks this.
4. **The route is public, so its security comes first.** Anyone on the internet can call
   `/api/cron/heartbeat`. Getting the `CRON_SECRET` check right on a route that does nothing is safer
   than getting it right for the first time on one that writes data.

### 1. Check the docs and facts

1. Re-read `node_modules/next/dist/docs/01-app/01-getting-started/15-route-handlers.md`. Only `GET`
   handlers can be prerendered or cached; a `POST` handler always runs at request time.
2. Re-read Vercel's Schedules docs ("Schedules", "Handling Scheduled Runs", "Schedules Concepts",
   "Schedules Configuration Reference", "Schedules Limits"). Facts checked on 2026-11-15:
   - Schedules are in **public beta**: "Behavior, APIs, and limits may change before general
     availability." Cron Jobs are legacy and "will be migrated to Schedules in the future".
   - Static schedules live under `schedules` in `vercel.json`, keyed by a stable name. Renaming one
     creates a new schedule with no history.
   - A **path** target sends an HTTP request to a route, `POST` by default, with
     `Authorization: Bearer <CRON_SECRET>` when `CRON_SECRET` is set, plus `ce-*` headers that include
     the run's execution ID (`ce-id`), which stays the same if a run is delivered twice.
   - Hobby: up to 100 static schedules per deployment, 5,000 runs per billing period (scheduled and
     manual runs both count), at most every 15 minutes, always within a 15-minute jitter window. Runs use
     ordinary function invocations; no separate charge is listed.
   - `timezone` takes an IANA name and follows daylight saving time; the default is UTC.
   - Production schedules start active; Preview branch schedules start inactive.
   - Path and function targets are not retried on failure. A run can arrive twice, or be skipped if
     Vercel can't deliver it before it expires.
   - A deployment keeps the `CRON_SECRET` it was built with, so a change needs a redeploy.
3. Check whether Vercel reads `engines.node` from `package.json` for the Node.js version. If it does, set
   `"engines": { "node": "24.x" }` so the version lives in the repository; otherwise rely on the project
   setting (Manual Task 3.4) and leave `package.json` alone.
4. Confirm `syd1` is Sydney (`ap-southeast-2`) and that Hobby allows one region of your choice.
5. Confirm the `git.deploymentEnabled` syntax for turning off deployments from `development`, and check
   whether a single setting can turn off every non-production branch instead.
6. Check whether the `vercel.json` schema at `https://openapi.vercel.sh/vercel.json` accepts `schedules`,
   so the editor doesn't flag it.

### 2. `vercel.json`

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "regions": ["syd1"],
  "schedules": {
    "heartbeat": {
      "schedule": "0 3 * * *",
      "timezone": "Asia/Singapore",
      "path": "/api/cron/heartbeat"
    }
  },
  "git": { "deploymentEnabled": { "development": false } }
}
```

- `requestMethod` is left out, so Vercel sends `POST`, its default for path targets.
- `jitter` is left out: Hobby always uses 15 minutes, so the run starts between 03:00 and 03:15.
- The `git` block uses the syntax checked in step 1.5.
- `next.config.ts` has no `trailingSlash`, so the path needs none.

### 3. The secret check: `lib/cron/authorize.ts`

```ts
export type CronAuthResult = "ok" | "unauthorized" | "not-configured";
export function authorizeCron(authorizationHeader: string | null, secret: string | undefined): CronAuthResult;
```

- Returns `"not-configured"` when the secret is unset or empty. The route then refuses every request:
  it fails closed.
- Returns `"unauthorized"` when the header is missing or isn't exactly `Bearer <secret>`.
- Compares the header with the expected value in constant time: hash both with SHA-256 and compare the
  digests with `crypto.timingSafeEqual`, so values of different lengths compare safely.
- Takes the header and secret as arguments, rather than reading `process.env` or the request itself, so
  it is a pure function that's easy to test. It never logs either value.
- Server-only: it imports `node:crypto` and lives in `lib/`, which only server code imports.

### 4. The database check and the route

1. **`lib/db/health.ts`** exports `checkDatabase(): Promise<void>`, which runs
   ``db.$queryRaw`SELECT 1` `` and throws if it fails. It's marked `server-only` like `client.ts`, reads
   no user data and needs no `userId`, since it touches no table.
2. **`app/api/cron/heartbeat/route.ts`** exports only `POST(request: Request)`:
   1. `authorizeCron(request.headers.get("authorization"), process.env.CRON_SECRET)`;
      - `"not-configured"` → **500** `{ error: { code: "CRON_NOT_CONFIGURED", message: "Scheduled jobs are not configured." } }`
      - `"unauthorized"` → **401** `{ error: { code: "UNAUTHORIZED", message: "Unauthorized." } }`
   2. `await checkDatabase()`;
      - on failure → **503** `{ error: { code: "DATABASE_UNAVAILABLE", message: "Database check failed." } }`,
        and log one line with the error's `name` and the run's `ce-id` header only. Prisma errors can
        include the host, so the message and stack are not logged.
   3. **200** `{ data: { database: "ok" } }`.

   Responses use `Response.json` with `Cache-Control: no-store`. No work is done for a refused request.
   The heartbeat is safe to run twice, since it changes nothing.
3. Other methods get Next.js's default 405, since only `POST` is exported. A browser or crawler visiting
   the URL therefore gets 405 and never reaches the secret check.

## Decisions

- **Schedules instead of Cron Jobs (owner's decision, 2026-11-15):** Cron Jobs are legacy and will be
  migrated, so starting on Schedules avoids a migration later. Schedules also add a time zone, 15-minute
  precision on Hobby instead of "any time within the hour", run history per schedule, and a way to run or
  pause a schedule without redeploying. The cost is that Schedules are in beta and may change; the route
  code doesn't depend on anything beta (see the next decision), so a change would most likely only touch
  `vercel.json`.
- **Path target with `CRON_SECRET`, not a private function target:** a function target has no public URL,
  which is safer, but it needs a standalone `api/*.ts` Vercel function with an `experimentalTriggers`
  setting and the `@vercel/schedules` package, outside Next.js's `app/` routes. That's experimental, and
  it's untested alongside a Next.js app on Vercel. A path target is an ordinary Next.js Route Handler that
  CI and Playwright already know how to build and test. Switching later is possible and is noted for
  Phase 3.
- **`POST`, not `GET`:** `POST` is Schedules' default, and Next.js never prerenders or caches a `POST`
  handler, so there's no chance of a cached response hiding a run. It also means a browser visiting the
  URL gets 405.
- **Daily `SELECT 1`, not more often (owner's answer 4):** Hobby allows every 15 minutes, but a daily
  check is enough to prove the connection and is well inside Supabase's 7-day pause window. Every 15
  minutes would use about 2,900 of the 5,000 monthly runs on a check that rarely changes.
- **03:00 in the owner's time zone:** a quiet hour, so the run doesn't compete with the owner using the
  app, and logs line up with the owner's day. Phase 3 and Phase 4 each pick their own time.
- **One route and one schedule per job:** Schedules make separate times cheap, and exchange rates
  (after the European Central Bank publishes, around 16:00 Central European Time) and recurring posting
  (after midnight in the owner's time zone) need different times. This replaces the earlier idea of one
  shared daily route. All scheduled routes share `lib/cron/authorize.ts` and the conventions in
  `code-standards.md`.
- **Previews off (owner's answer 2):** CI already checks every push, and previews would put the
  development database string in a second place. Revisit in Phase 1.
- **Vercel never runs migrations:** the build gets no `DIRECT_URL`, and production schema changes stay
  the owner's manual `migrate status` then `migrate deploy` routine. A failed or half-applied migration
  inside a build would be harder to see and recover from, and it would put a second production string in
  Vercel.
- **No `@vercel/schedules` package:** the path target doesn't need it, and the run's execution ID can be
  read from the `ce-id` header if a later job needs it. Adding a beta package waits for a real use.
- **Constant-time secret comparison:** Vercel's example compares with `!==`. Hashing and
  `timingSafeEqual` costs one line and removes a timing side channel on a public URL.
- **Fail closed:** an unset `CRON_SECRET` refuses every request (500, so the misconfiguration is visible
  in the logs) instead of running the job unprotected.
- **Placeholder `DATABASE_URL` in CI instead of a lazy client:** `lib/db/client.ts` stays as it is, and
  nothing connects to the placeholder. Making the client lazy can wait until there's another reason to
  change it.
- **Region `syd1`:** both Supabase projects are in `ap-southeast-2`; a different region would add a
  long round trip to every query.
- **No custom domain:** no domain is owned, and buying one is a paid service.
