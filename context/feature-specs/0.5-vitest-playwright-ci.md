# 0.5 Vitest, Playwright, Lint and Build in CI

**Phase:** 0, Foundation
**Status:** In progress (approved by the owner on 2026-11-15); waiting for the first CI run
**Depends on:** Unit 0.4 (first migration with RLS)

## Goal

Give FinTrack an automated safety net before any feature code exists. When this unit is done:

- `npm test` runs Vitest unit tests, with no database or secrets needed;
- `npm run test:db` runs database tests, and the first one guards invariant 4: every table in `public`
  has RLS on and no policies (the automated check deferred from unit 0.4). Database tests run only on CI,
  against a throwaway Postgres, and never against either Supabase project;
- `npm run test:e2e` runs Playwright against a production build, and the first test covers the app
  shell's main flow on desktop and at phone width;
- a GitHub Actions workflow runs lint, type checking, unit tests and the build, applies every migration to
  a throwaway Postgres and runs the database tests against it, and runs the Playwright tests;
- the testing conventions are written down for later units.

## Scope

**In scope**

- Vitest, configured with two projects: `unit` (no database) and `db` (CI's throwaway Postgres only)
- Playwright with Chromium only, in a desktop and a phone-width project
- First tests: navigation items and the RLS check's logic (unit), RLS on every table (db), and the app
  shell (e2e)
- `package.json` scripts: `test`, `test:watch`, `test:db`, `test:e2e`, `typecheck`
- `.github/workflows/ci.yml`, with a Postgres service container for the database job
- `.nvmrc`, so CI and local use the same Node major version
- Ignore entries for Playwright's output in `.gitignore` and `eslint.config.mjs`
- Doc updates in `architecture.md`, `code-standards.md` and `progress-tracker.md`

**Out of scope**

- Running database tests locally, or against any Supabase project (owner's decision, see Decisions)
- React Testing Library, `jsdom` and `@vitejs/plugin-react`: no component needs a unit test yet. The
  first unit that does adds them.
- A Vitest alias for `server-only`: no test imports `lib/db/client.ts` yet. Phase 1's first data-layer
  test adds it (see Notes).
- The cross-user access test pattern (the first feature that stores user data, in Phase 1)
- Firefox and WebKit, visual regression, accessibility scanning (`axe`) and coverage thresholds
- Vercel, preview deployments and the cron route (unit 0.6)
- Supabase Auth environment variables in the CI build (Phase 1)
- Dependency scanning and Dependabot (Phase 12)
- Any change to app code, `next.config.ts`, `prisma/` or `.env*` files

## Implementation

Do not start until the owner approves this spec.

### 1. Check the docs and versions

1. Re-read `node_modules/next/dist/docs/01-app/02-guides/testing/vitest.md` and `playwright.md`.
2. Check the current stable versions with `npm view`. On 2026-11-13: `vitest` 5.1.0 (released
   2026-11-02), `@playwright/test` 1.65.0, `vite` 8.3.8. Use stable releases only, never a beta, alpha or
   release candidate, and pin exact versions as for Prisma.
3. Read the Vitest 5 docs on `test.projects`, and the Vite docs on whether `resolve.tsconfigPaths` is
   built in. If it is, use it; otherwise add `vite-tsconfig-paths` as the Next.js guide does.
4. Check the current major versions of `actions/checkout`, `actions/setup-node` and
   `actions/upload-artifact`.
5. CI's Postgres container uses major version 17, matching Supabase. The owner checked the development
   project's `server_version` in the SQL Editor on 2026-11-15: 17.11. Use the official `postgres:17` image.

### 2. Vitest

1. Install `vitest` (and `vite-tsconfig-paths` only if step 1.3 requires it) as exact dev dependencies.
2. Create `vitest.config.mts` with the `@/` alias and two projects:
   - **`unit`:** `tests/unit/**/*.test.ts`, `environment: "node"`.
   - **`db`:** `tests/db/**/*.test.ts`, `environment: "node"`, `setupFiles: ["tests/db/setup.ts"]`, and
     files run one at a time (`fileParallelism: false`), since later tests will write to the same
     database.
3. Tests import `describe`, `test` and `expect` from `vitest` explicitly. No globals.
4. `tests/db/setup.ts` loads no env files. It reads `DIRECT_URL` from the environment, which only CI sets,
   and stops the run before any test starts:
   - if `DIRECT_URL` is unset: "Database tests run on CI against a throwaway Postgres. See
     context/code-standards.md.";
   - if its host ends in `supabase.com` or `supabase.co`: "Database tests never run against Supabase."
     This also covers a production `DIRECT_URL` left set in the shell after a migration.

   Neither message includes the connection string.

### 3. First tests

1. **`tests/unit/nav-items.test.ts`** guards the decision that no navigation link leads to a 404:
   - every item in `mainNav` and `accountNav` has a unique `href` and `title`;
   - `getNavItem` returns the item for each `href`, and throws for an unknown one;
   - each `href` has a matching `app/(app)/<segment>/page.tsx` file.
2. **`tests/db/rls.test.ts`** connects with `pg` through `DIRECT_URL` (not Prisma, which stays inside
   `lib/db`), reads only the system catalogs, and asserts:
   - `public` has at least one table, so the test can't pass on an empty database;
   - no table in `public` (`relkind` `r` or `p`) has `relrowsecurity = false`;
   - `pg_policies` has no row for `schemaname = 'public'`.
     On failure, it names the offending tables. It prints no connection details.

   The check that turns catalog rows into a list of problems is a small pure function in
   `tests/db/rls-check.ts`. A unit test, `tests/unit/rls-check.test.ts`, feeds it made-up rows (a table
   with RLS off, a policy) and confirms it reports them by name. This proves the RLS test can fail without
   creating a bad table anywhere.

3. **`tests/e2e/app-shell.spec.ts`**:
   - `/` redirects to `/dashboard`, whose `h1` is "Dashboard";
   - **desktop:** clicking each sidebar item opens its page, with the matching URL and `h1`;
   - **phone (375px wide):** the "Open menu" button opens the sidebar, choosing "Transactions" opens that
     page and closes the menu;
   - **phone:** no app page scrolls horizontally (`scrollWidth` is not larger than `clientWidth`).

### 4. Playwright

1. Install `@playwright/test` as an exact dev dependency, and download Chromium with
   `npx playwright install chromium`. Do not use `npm init playwright`, which adds example files.
2. Create `playwright.config.ts`:
   - `testDir: "tests/e2e"`, `baseURL: "http://localhost:3000"`;
   - projects **`desktop`** (Desktop Chrome, 1440×900) and **`phone`** (Chromium, 375×812, touch);
   - `webServer`: `npm run start` on port 3000, reusing an existing server outside CI. Tests run against
     a production build, as the Next.js guide recommends, so `npm run build` runs first;
   - on CI: `forbidOnly`, 2 retries, one worker, traces on first retry, and the HTML report.
3. Add `/playwright-report/`, `/test-results/`, `/blob-report/` and `/playwright/.cache/` to
   `.gitignore` and to the ESLint ignores.

### 5. Scripts and Node version

1. Add to `package.json`:

   ```json
   "typecheck": "tsc --noEmit",
   "test": "vitest run --project unit",
   "test:watch": "vitest --project unit",
   "test:db": "vitest run --project db",
   "test:e2e": "playwright test"
   ```

2. Create `.nvmrc` with `24`, matching the local Node 24.19.0. Unit 0.6 sets Vercel to the same major.

### 6. CI workflow

Create `.github/workflows/ci.yml`:

- **Triggers:** pushes to `development` and `main`, pull requests into `main`, and `workflow_dispatch`
  for a manual "Run workflow" button. `concurrency` groups runs by branch, and a new push cancels an
  older run only on `development` and pull requests. Runs on `main` are never cancelled, so every push to
  `main` gets a complete result.
- **Permissions:** `contents: read` only. No secrets are used. The repository is public, so logs and
  uploaded reports are public too; nothing may print connection details or personal data.
- **Every job:** checkout, `setup-node` with `node-version-file: .nvmrc` and the npm cache, then
  `npm ci`. Its `postinstall` runs `prisma generate`, which works without `DIRECT_URL` (unit 0.3).
- **`checks`:** `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`.
- **`db`:** a `postgres:17` service container (step 1.5), with a health check and
  a throwaway password written in the workflow file, since the database exists only for the run.
  `DATABASE_URL` and `DIRECT_URL` both point at it on `localhost`. Steps: `npx prisma migrate deploy`,
  `npx prisma migrate status`, `npm run test:db`.
- **`e2e`:** `npm run build`, `npx playwright install --with-deps chromium`, `npm run test:e2e`, and
  upload `playwright-report/` as an artifact when the job fails, kept for 7 days.

The three jobs run in parallel. Pin each action to its current major version (step 1.4). The `checks`
and `e2e` jobs each run `npm run build`; this is deliberate (see Decisions).

### 7. Run everything locally

1. `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`, `npm run test:e2e`.
2. Run `npm run test:db` with no `DIRECT_URL` set, and confirm it stops with the "run on CI" message
   before any test runs. Do not run it with any Supabase string.
3. Break the unit test on purpose once (change an expected `href` in the test) and confirm it fails with a
   useful message, then revert it. The RLS test's failure path is covered without a database by the
   unit test in step 3.2.

With the owner's approval (Manual Task 2), commit the unit and push it to `development`. Confirm all
three jobs pass, and record the run's duration in Notes.

## Decisions

- **Database tests run only on CI's throwaway Postgres (owner's decision, 2026-11-15):** each run starts
  an empty Postgres on GitHub's machine, applies every migration with `migrate deploy`, runs the tests and
  discards the database. It needs no secrets, never touches Supabase data, never pauses, and proves the
  migrations build a database from nothing. It lacks Supabase's `anon` and `authenticated` roles, so the
  grant checks from unit 0.4 stay a manual check through Security Advisor.
- **No local database tests (owner's decision, 2026-11-15):** Phase 1's cross-user tests will write data,
  and the owner doesn't want test data in the development project. CI gives the same coverage, a few
  minutes later. `.env.test.local` was deleted, and `tests/db/setup.ts` refuses Supabase hosts.
- **Public repository (owner, 2026-11-15):** Actions minutes are free and unlimited, so all three jobs run
  on every push, and branch protection on `main` is available for free.
- **CI triggers:** pushes to `development` (where work happens) and `main`, pull requests into `main`, and
  a manual "Run workflow" button.
- **Two Vitest projects instead of one:** unit tests stay fast and need no secrets, so `npm test` always
  works locally. Database tests are explicit about needing CI's database.
- **Postgres 17 on CI:** matches Supabase (17.11, checked by the owner on 2026-11-15).
- **The production build runs in both `checks` and `e2e` (deliberate):** running the jobs side by side
  keeps the whole run faster than making `e2e` wait for `checks`, and on a public repository the extra
  minute of build time costs nothing.
- **Cancel superseded runs only on `development` and pull requests:** saves time where pushes come in
  quick succession, while every push to `main` keeps a complete result.
- **Chromium only:** the app has no browser-specific code yet. Phone width is covered by a second
  Chromium project.
- **Playwright runs against `next start`:** as the Next.js guide recommends, and it matches what Vercel
  serves.
- **No component-testing libraries yet:** added with the first component unit test, per "no abstractions
  until a second real use needs them".

- **Actions:** `actions/checkout@v7`, `actions/setup-node@v7` (explicit `cache: npm`) and
  `actions/upload-artifact@v7`, the current majors on 2026-11-15.

  ESLint/TypeScript chain), none from this unit's packages. Left for Phase 12's dependency scanning.
